# 账户表结构草案

> **定稿 · 2026-11-25**　本文件即账户侧最终表结构；《资产表结构草案.md》第七节与《项目规范与契约.md》4.2 均指向本文件。草稿全文另存 `账户表结构草案_草稿存档.md`，仅供对照，不再作为依据。
>
> **交付边界**：只给表结构，没动仓库代码、没改业务层、没出代码补丁。按约定，「稿件已定、代码未跟上」不计入待决项。
> 全部为 SQLite DDL，沿用 `account_db.dart` / `credit_card_rule.dart` 的写法（`IF NOT EXISTS`、无外键、枚举不写 CHECK）。
> `book_id` 是账本分组，多账本预留，当前恒为 `'default'`。
>
> **与《资产表结构草案.md》并列，不是替换**：那份管 `az_assets*` / `az_liabilities*` / `az_asset_*` / `az_liability_*`，本份管 `accounts` / `account_*` / `credit_card_rules`。两处「旧表全部删除」各管各的前缀，合起来才是最终库表全集，**互不覆盖、互不删除对方的表**。
> 本文件承接资产草案第七节点名的三句契约、方案 A 三列、四类账户类型，并在第七节逐条核对。
>
> **能力边界（补充定稿）**：本软件是**财务记录分析软件，只有记录能力**，不具备任何实际财务功效。文中「新增 / 删除账户」「开卡 / 注销卡」「账户间转账」一律指**记录**：新增一张卡 = 记录用户手上多了一张什么样的卡；删除 / 归档一张卡 = 从记录里去掉这张卡；账户间转账 = 记录用户已经从哪张卡把一笔款转移到了另一张卡。软件**不实际开卡、不实际注销卡、不实际转账、不代扣代付**，也不与银行或任何真实账户连接；账本里的余额与流水都是用户录入事实后推算的记录数，不是真实资金变动。凡功能描述中写明软件实际具有上述能力的表述，一律删除，只保留记录口径。

D1 乙原描述为「新次表放两列」。定稿**只放一列 `net_transfer_in`**，「剩余可用额」仍复用主表 `balance`：

> 若把「剩余可用额」也物化进次表，就与主表 `balance` 形成第二份余额，违反 A12「账户流水是唯一写入点」与 10.9「不重复加」。主表 `balance` 本身就是**存下来的**数，已满足「要存剩余可用额」；次表只多存主表没有的「净转入额」。

### 0.4 术语澄清：「出账」有两个意思，别写岔

| 词 | 指什么 |
|---|---|
| **消费出账** | 单笔 `direction='out'` 的 `credit_spend` 流水（每刷一笔一次） |
| **账单出账 / 出账后清零** | **账单日结账、生成本期账单、进入下一期**。「每次出账后清零」指这一个 |

`current_period_spent` 归零发生在**账单出账**时，不是每笔消费后。归零仍按全局约定 7「打开时现算、不做定时任务」，由 `last_period_key` 判跨周期。

### 全局约定

**1. 旧表处置**：账户侧原有 4 张表（`accounts` / `account_category_bindings` / `account_entries` / `credit_card_rules`）**全部删除，以本文件新表为准**。不做旧数据迁移；如需留存历史，另走一次性导出。资产侧、负债侧前缀的表不在本文件处置范围内。**两份草案必须全库一次性重建**：资产侧 `link_account_id` 单向指向 `accounts.id`，分模块先后重建会留下静默悬空引用。

**2. 金额一律 `TEXT` 存十进制字符串，计算走统一工具类**

- 落库格式硬契约：`^-?\d+(\.\d{1,2})?$`；**最多 2 位小数**；禁千分位、科学计数法、前后空格、前导 `+`；`DEFAULT '0'`；空值由业务层兜底 `'0'`。
- **允许负号**，且这是真实用例：A3 坏账 `total_gain` 可为负、4.7 允许负余额、`balance_after` 可为负、`net_transfer_in` 可为负。数值范围 CHECK 统一写 `CHECK (CAST(列名 AS REAL) ...)` 只做兜底；**下列列不加 `>= 0`**：`balance` / `balance_after` / `net_transfer_in`。
- **工具类 `Money`（全库只一份，放 `lib/utils/`，各模块不得另写 parse）**：`parse(String) → int`（单位：分）、`format(int) → String`、加减全用 `int`。**内部若用 `double` 会把精度重新丢回去**（`0.1+0.2 != 0.3`），与「保存不丢精度」自相矛盾，故禁止。不引第三方依赖。
  ```
  库里 '833.33'  →  parse → 83333(int，分)  →  int 加减  →  format → '833.33'
  ```
- 模型层：`fromMap` 用 `Money.parse(m['balance'] as String?)`，**删掉 `(as num?)?.toDouble()`**（TEXT 读成 `String`，`as num?` 会抛 TypeError）；`toMap` 用 `Money.format`。`AccountBalanceRule.delta` 返回 `int`，`AccountEntryDao.append` 整数加。展示层 `MoneyFormat` / 最低还款估算 / 还款提醒统一走工具类格式化。
- **利率、费率、比例、周期数值、数量仍 `REAL` 小数**（5% 写 `0.05`、日利率万五写 `0.0005`），不是金额，不受本条约束。文档里的金额示例一律以**元**叙述，落库存同值字符串，不 ×100。
- 名义金额：账本里记的都是当时填下的钱数，软件不自动调大调小（3.8 / 13.1 / 10.9）；账户表不建任何「实际购买力」列。

**3. 枚举规则**：**所有枚举列都不写 CHECK**，注释写明允许值并在下表列全，由业务层校验。
> **CHECK 分两类，只去第一类（C7①）**：① **枚举取值 CHECK**（`kind IN(...)` / `direction IN(...)` / `entry_type IN(8 值)` / `interest_method IN(...)`）全部去掉，交给业务层，理由：加形态 / 加流水类型不能被迫重建整表；② **跨列业务一致性 CHECK 与数值范围 CHECK 全部保留** —— 数值范围（`amount > 0`、`initial_balance >= 0`、比例 `0~1`、天数 `1~31`）一直在 DDL 里，四条跨列 CHECK 按 C7① **原样恢复**（主表 1 条 + 流水表 3 条，见两处 DDL 与第四节第 6 条）。「由业务层管」只适用于枚举取值，不适用于这两类。

| 列 | 允许值（含义） |
|---|---|
| `kind` | `liquid`（流动资金账户）/ `credit`（信用卡账户）/ `restricted`（其他资金账户）/ **`investment`（投资账户＝股票账户）**。**四类一张主表**，不按类拆表 |
| `type` | `bank` / `cash` / `wechat` / `alipay` / `credit_card` / `huabei` / `jiebei` / `social_security` / `housing_fund` / `gift_card` / `frozen` / **`stock_account`** / `other`。**四张清单互不相交**：K1 用前 4 项 + `other`；K2 用 `credit_card` / `huabei` / `jiebei`；K3 用 `social_security` / `housing_fund` / `gift_card` / `frozen` / `other`；**K4 只有 `stock_account`**。由 `allowedTypesFor(kind)` 唯一真源校验，DDL 不锁取值（v5 教训：写死 CHECK 加形态要重建整表） |
| `direction` | `in`（入账）/ `out`（出账）。**描述资金往哪走，不描述累计值怎么变**；信用卡规则下累计值增减取反 |
| `entry_type` | `opening` / `expense` / `income` / `transfer_out` / `transfer_in` / `adjustment` / `credit_spend` / `credit_repay` / **`asset_buy`（投资账户买入扣款）** / **`asset_sell`（卖出到账）** / **`interest`（账单出账息费，C9-c 由预留转正式）**。**预留**：`loan_in` / `reimburse`，随对应模块开工直接加值，不写 CHECK、不重建流水表。**出入账分组**：消费类 / 还款类两组、三个统计视图见全局约定 10；出账与入账各自关联哪张业务单据见全局约定 11 |
| `record_source` | `user`（用户主动记的一笔）/ `auto`（**仅**软件在**账单出账动作**里自动带出的息费那条 `entry_type='interest'`；转账两条、还款两条都 `user`） |
| `interest_method` | `''`（未填）/ `full`（全额计息）/ `unpaid`（只按未还部分计息） |
| `ref_type` | **按「指向哪个模块的哪类单据」取值，列全如下**（不写 CHECK，由业务层校验；`ref_id` 与之配对定位一行）：<br>• `expense` → 支出模块**支出记录**<br>• `income` → 收入模块**收入记录**<br>• `liability_inflow` → 债务模块**收款记录**（放款到账 / `az_liability_loan_draw` 支取）<br>• `liability_repay` → 债务模块**还款记录**（`az_liability_loan_repay.id` / `az_liability_installment_repay.id` / 信用卡账单周期标识）<br>• `asset_inflow` → 资产模块**收款记录**（借出的钱收回 / 卖出到账 / 分红到账）<br>• `asset_buy` / `asset_sell` → 资产模块买卖批次记录<br>• `debt_cost` → 界面标签「借钱的成本」，账单出账 `interest` 那条专用、**无负债侧行**（`ref_id` 可空）<br>• `liability` / `asset` → 负债主表 / 资产主表的松关联（原有取值，保留）<br>• `transfer` / `adjustment` / `statement` → 账户侧自身（转账配对 / 余额调整 / 账单周期）<br>完整分组与约束见全局约定 11。`ref_type` 可空：未来模块未开工、或本就无对应单据时不填 |
| `archived` / `is_liquid` / `include_in_net_worth` / `non_binding` / `liquid_locked` / `monthly_compound` / `cash_advance_interest_free` | `0` / `1`；`liquid_locked=1` 表示社保 / 公积金强制不可花且开关禁用 |

> **B3 枚举兜底硬要求**：`AccountKind.fromDb` / `AccountType.fromDb` / `AccountEntryType.fromDb` 必须为 `investment`、`stock_account`、`asset_buy` / `asset_sell` 加**显式分支**，默认分支改 `unspecified` 或抛错。**禁止 `_ => liquid` / `_ => opening` 兜底**——否则新建的投资账户一读回来变回流动资金账户、资产买卖流水显示成「初始余额」，而 `opening` 是唯一能凭空产生余额的动作。

**4. 账户类型编号对照**（后文写成「编号（中文名）」）

| 编号 | 中文名 | 次表 | 说明 |
|---|---|---|---|
| K1 | 流动资金账户 | **无** | 钱能自由花；对应资产草案「储蓄账户」 |
| K2 | 信用卡账户 | `account_credit` | 先消费后还款；花呗 / 白条归这里 |

**6. 易混字段释义**

| 字段 | 在哪 | 业务含义 | 谁填 |
|---|---|---|---|
| `balance` | 主表 | **累计值**。K1/K3 = 当前余额；K2 = **已用额度（欠款）**；**K4 = 剩余可用额**。由流水推导、禁止手填（10.9 单写点）；可为负 | 软件写，唯一写入点 `AccountEntryDao.append` |
| `initial_balance` | 主表 | 登记账户时唯一允许手填的数字，本身也是一条 `opening` 流水（3.8）；仅储蓄类 | 用户 |
| `credit_limit` | K2 次表 | **总额度**，这张卡最多能花多少 | 用户 |
| `available`（不建列） | — | 可用额度 = `credit_limit − balance`，永远算出来（3.4） | 软件算 |
| `current_unpaid`（**不建列**） | — | **当前未还 = 这张卡现在欠多少，直接就是主表 `balance`**。办分期时卡上欠款不动、每还一期两边各减一次，分期剩余本金是债务侧的明细、不与 `balance` 相加（相加会把同一笔钱算两遍）；不建列，打开时现算（C4① 已删列） | 软件算 |
| `current_period_spent` | K2 次表 | **本账单周期新增消费额**（方案 A 三列之一）。`credit_spend` 流水由 `append` 同事务累加；**账单出账时归零**，开始计算下期 | 软件写 |
| `period_installed_amount` | K2 次表 | **本周期已办分期额**（方案 A 三列之一），办挂卡分期通过后累加 | 软件写 |
| `last_period_key` | K2 次表 | **上次归零所属账单周期**，如 `'2026-03'`；判断跨期用，不做定时归零 | 软件写 |
| `net_transfer_in` | K4 次表 | **净转入额** = Σ 外部储蓄账户转入 − Σ 转出到储蓄账户。**可为负**；卖出到账**不计入**；买入扣款**不减** | 软件写 |
| `min_payment_rate` | K2 次表 | 最低还款比例，10% 写 `0.1`；是比例不是金额，用 `REAL` | 用户 |
| `daily_rate` | 章程表 | 日利率，万五写 `0.0005`；`REAL`；用户手填，软件不联网查 | 用户 |
| `grace_amount` | 章程表 | 容差金额，是金额，按全局约定 2 用 `TEXT` | 用户 |
| `amount` | 流水表 | **恒为正**的一笔钱（10.6）。表示减少用 `direction`，不存负数 | 用户 / 软件拆出 |
| `balance_after` | 流水表 | 这笔发生**之后**的累计值，逐笔可审计；可为负 | 软件写 |
| `credit_limit_after` | 流水表 | 这笔发生**之后**该卡的总额度，**逐笔时点快照**；可用额度 = `credit_limit_after − balance_after`；调额后回看旧流水仍精确（v7 起）。储蓄类 / K4 恒 NULL | 软件写 |
| `ref_type='debt_cost'` | 流水表 | **账单出账息费**那条（`entry_type='interest'`，本金之外的利息 + 费用）：只作界面标签「借钱的成本」，K2 欠款增加、**不进三个统计视图**。净资产视图里在账单出账时记一次、还款不重复（7.12 / C9-c / 全局约定 9）；支出统计里息费随还款 `credit_repay` 计一次、不另计（全局约定 10）。信用卡类无负债侧行，`ref_id` 可空；贷款 / 分期还款改用 `ref_type='liability_repay'` + `ref_id` 对齐（全局约定 11） | 软件写 |
| `non_binding` | 流水表 | 用了受限账户但不在绑定用途里（3.5 软约束破例） | 软件标 |
| `reason` | 流水表 | 余额调整必填原因；`adjustment` 时为空拒绝保存 | 用户 |
| `transfer_group_id` | 流水表 | 一笔转账两条流水配对（3.7），**不另建转账表**；**还款 2 条等值流水同样用此配对**并互指 `counterparty_account_id`，但 `entry_type='credit_repay'`、不是转账、不复用 `transfer` 实现（C9-b） | 软件写 |
| `principal_part` / `interest_part` | **不建列** | 本息费在**账单 / 负债附表**里拆，账户侧**不拆成多条流水**；还款恒定 2 条等值，见全局约定 9（C9-c） | — |
| `sort_order` | 主表 | 拖拽排序（3.7），一次事务批量写 | 软件写 |

**7. 运行模型：流水只能在「新建」和「记账动作」时生成（最高优先级约束）**

**软件在用户不打开应用的时候不处理任何数据**。因此：

- **流水只在两个时机产生**：①用户**新建**账户时写第一条 `opening` 流水（仅 K1/K3/K4；信用卡没有「期初已用额度」）；②用户**执行记账动作**（消费 / 收入 / 转账 / 还款 / 余额调整 / 资产买卖收付 / 投资账户转入转出 / **账单出账息费**）时，在一个事务里算出结果、写回流水、必要时带出成对的另一条。**「历史持仓补录」属①的例外**：只新建资产记录、明确不写账户流水（见下方专条）。
- **禁止定时生成**（每月 1 号自动记利息、账单日自动生成账单、月末自动存快照、跨账单日定时归零，全不成立）、**禁止一次生成全部计划**（建卡时排好 N 期还款计划不成立）。永远没有预排好的流水队列。
- **一次事务成组处理**：**还款 2 条等值**、转账一次 2 条、投资账户转入 / 转出成对 2 条、**账单出账息费 0 或 1 条**、**负债页还一期挂卡分期同事务触发账户侧 2 条**（契-1），**要么全成要么全滚**（3.7 / 附录 A / 10.9）。
- **打开 / 操作时按需补齐状态**：还款提醒、逾期判定、`current_unpaid` 现算、`last_period_key` 跨期归零、A1/A2 只读镜像、常用账户聚合，都在那一刻现算现标。**归零顺序关键：先滚动归零、再记本期消费**，否则新消费被误清（资产草案主表标注 8）。
- **归档态不产生流水**：归档账户**不能补记**，先恢复再记（S3）。

**历史持仓补录边界（契-14）**：开发 / 上线时用户可能**已经买入**，为方便直接创建基金或资产 → **不走账户扣款、不写账户流水**，只在资产侧生成记录。它属「新建」时机，但明确**不产生账户流水、也不产生债务待办记录**；补录持仓**不参与资金变动校验**，软件不倒推扣款、不报错。因此补录那一刻总资产增加、账户余额不变，是**有意的期初事实录入**，账本从这一刻起以此为起点，不是账实不符。之后正常买入选「扣款」才写账户出账流水；卖出 / 分红选「到账」才写入账流水；未选到账的历史收益同样按补录处理。此条同时是契-11「选不扣不写」的完整边界。

**8. 账户绑定口径**：**跨类按账户统计一律取主表 `accounts.id`**。资产主表 `az_assets.link_account_id`、负债主表 `az_liabilities.link_account_id`、分期次表 `mount_creditcard_id` 都**单向指回这里**，账户表不加悬空外键列。

- **绑定唯一真源**是 `account_category_bindings`，主表 / 次表不塞 JSON、逗号串；一个支出类型可被多个受限账户绑定（3.5）。
- **社保三道锁**：详情页不显示入口、表单防御、Controller 硬校验（`type='social_security'` 直接拒绝）；**公积金可以绑定**（3.5 房租例子），只锁社保。
- **可付账户查询 `payableAccountsFor`**：无绑定时按「不绑定也能用」返回全部可付账户；有绑定时 = 流动资金账户 + 信用卡账户 + 绑定了该类型的受限账户。**K4 投资账户显式排除**——它不是付款账户，不进记支出的下拉（A8）。
- **A1/A2 镜像只读**（6.2）：资产页由账户现场聚合，**不允许反改账户余额**；归档 / 软删后镜像标「已断开」，保留当时数值但不参与总账。

**9. 还款口径与记账方向**（C9-c）：账户侧不拆本息流水。本节「本金不是消耗、息费才是」与「净资产 = A − P − I − F」只服务**净资产视图**；**支出统计按收付实现制取数，见全局约定 10**。

- **账单出账息费**（链条 3 / 契-13）：用户打开 / 操作时按 `last_period_key` 判跨账单日 → **先归零**方案 A 两列、再进新周期；同一时刻按 `credit_card_rules`（`daily_rate` / `interest_method` / 7.7 算法）**在账户侧现算**本期利息 I + 费用 F。若 `I+F > 0` 写**一条** K2 出账流水 `entry_type='interest'` + `ref_type='debt_cost'` + `record_source='auto'` → `balance += I+F`；`I+F = 0` 不写。**打开时只算展示值**（本期应还、最低还多少、按日滚利息一次性补算），**不逐日生成流水、不落表；账单出账才写一次**。最低还款只是展示值、不是分期行、不生成逐期记录。这条 `interest` 流水只增加 K2 欠款、**不进三个统计视图**；息费在还款时随 `credit_repay` 计一次，不记第二遍（7.12 / 全局约定 10）。
- **还款恒定 2 条等值流水**（链条 4）：还款总额 `X = 本金 P + 利息 I + 费用 F`。一个事务两条、金额严格相等 —— ① 来源 K1 储蓄卡 `credit_repay` / `out` / X（`balance −X`）；② 信用卡 K2 `credit_repay` / `in` / X（已用额度 `−X`，credit 规则取反）。两条用 `transfer_group_id` 配对、`counterparty_account_id` 互指，`ref_type` 指向对应账单 / 负债还款行。**`interest=0` 仍是两条，不退化**；本息费在账单 / 负债附表拆，账户侧不拆成多条流水。
- **恒等验算**：`净资产 = A − P − I − F`，还款后卡欠款归零；本金是形态变换、净资产不变，息费已在账单出账扣过一次，还款不重复扣（10.9）。例：期初 A=30,000、消费 P=6,000、账单息费 I+F=235 → 卡欠款 6,235 → 还款 6,235 两条 → 净资产 23,765、卡欠款 0。
- **还款 ≠ 转账**（C9-b）：`entry_type` 是 `credit_repay`，**不是** `transfer_out/in`；实现走独立 `repay`，绝不调用储蓄类 `transfer`。配对只是复用两列，不是复用实现。
- **配套硬校验**：`transfer` 的 `counterparty_account_id` **禁止指向 `kind='credit'` 的账户**。不补这条，用户能从转账路径绕进信用卡，把利息当本金减掉。
- **净资产口径与支出统计口径分开**：上文「本金不是消耗」「净资产 = A − P − I − F」说明本金形态变换不改变净资产；买股票 2 万只是账户 −2 万、持仓 +2 万，净资产不变（3.7 / 6.5 / 10.9），在支出统计里属 `asset_buy`、两类都不算。「这个月花了多少」按收付实现制取数，**见全局约定 10**，不按本节净资产口径取。

**10. 出入账分组与三个统计视图**（支出统计口径）：钱从**存储账户**出去多少，就按流水 `amount` 全额计多少，不分本金利息。**入账记录与出账记录一样分组**（直接类 / 间接类），只是统计视图只取 `direction='out'` 那一侧；入账那侧分什么组、关联哪张单据，见全局约定 11。

**统计口径是收付实现制**：新增资产若没走账户出账（如凭空多一套房产、历史持仓补录），不算支出；该资产的价值由房贷每期从存储账户定期出账逐期划出。

**存储账户**指 K1 流动资金账户，以及 K3 / K4 中实际存有资金、可对外付款的账户；**K2 信用卡账户不是存储账户**——`credit_spend`、`interest` 动的是额度与欠款，不是卡里的钱，不进出账统计。

**先限定范围再分组**：只有「非 K2 账户 + `direction='out'`」的流水进入统计，再按 `entry_type` 分两组：

| 组 | `entry_type` | 含义 |
|---|---|---|
| **消费类出账（直接出账）** | `expense` | 钱直接付给商户 / 对手，当场换回商品或服务 |
| **还款类出账（间接出账）** | `credit_repay` 中 `direction='out'` 那条（付款卡） | 信用卡 / 分期 / 贷款还款；金额 = 当期实还总额（含本金、利息、费用），是此前一笔消费 / 放款的后续 |
| **两类都不算** | `credit_spend`、`interest`、`credit_repay` 中 `direction='in'` 那条、`transfer_out` / `transfer_in`、`asset_buy` / `asset_sell`、`adjustment`、`opening` / `income` | 额度与欠款变动、转账、资产买卖形态转换、余额调整 |

**三个统计视图**：

| 视图 | 取数 |
|---|---|
| **生活成本** | 消费类出账 |
| **实际支出** | 消费类 + 还款类出账 |
| **资产抵消** | 还款类出账（每月通过还款把此前未走账户出账就形成的资产价值逐期划出） |

资产抵消是实际支出的子集，同源、不重复写数；情境模拟「能撑几个月」按 K1 存储账户**全部**出账取数，不按这三个视图取数。这三个视图属统计层，不改主表「看板口径」里的账户余额聚合。

**不双计**：同一笔信用卡消费，`credit_spend` 那天不计，只在还款月由 `credit_repay` 计一次还款类；账单出账那条 `interest` 也不另计（息费已含在还款金额里）；同一笔贷款月供整笔计还款类，不再按负债附表的 `interest_part` / `fee` 另计一次。

**与债务侧 `total_loss` 的关系**：`total_loss` 是「这笔债一共多付了多少钱」的债务维度展示，不是这三个视图的取数来源；两处不相加、不互相代用。本息拆分（`principal_part` / `interest_part` / `fee`）仍保留在负债附表，只服务负债侧计算。

**取数不依赖 `ref_type`**：三个视图只按 `account_id → kind` 与 `entry_type` / `direction` 筛，记支出模块未开工也能算总额；`ref_type='debt_cost'` 只作界面标签，`category_id` / `payee` / `ref_type` 用于按品类拆解与单据关联。

**11. 出入账与业务单据的关联**（跨模块指向，**不加列、不加表**）

一条流水记的是「哪张卡、什么时候、钱进去还是出去、多少」；业务单据记的是「这笔钱是为什么」。两者用**已有的 `ref_type` + `ref_id` 两列**指过去：`ref_type` 说清是哪个模块的哪类记录，`ref_id` 是那张表里的行 id，以 `(ref_type, ref_id)` 组合定位（已有 `idx_entries_ref` 索引）。**不另建模块列、不建中间表、不把单据内容抄进流水**——`note` / `payee` / `image_ref` 只作展示。

**出账和入账完全对称**，都按「直接 / 间接」分两组，各自关联到对应模块：

| 方向 | 组 | `entry_type` | `ref_type` | `ref_id` 指向 |
|---|---|---|---|---|
| **出账** | 消费类（直接出账） | `expense` | `expense` | **未来支出模块的支出记录**（买菜、缴费这类当场换回商品服务的单据） |
| **入账** | 直接入账 | `income`、`reimburse`（退款，预留值） | `income` | **未来收入模块的收入记录**（工资、红包等当场收到钱的单据） |
| **出账** | 还款类（间接出账） | `credit_repay` 中 `direction='out'` 那条 | `liability_repay` | **债务模块的还款记录**：`az_liability_loan_repay.id` / `az_liability_installment_repay.id`；信用卡账单还款无负债侧行，指账单周期标识 |
| **入账** | 间接入账 | `loan_in`（放款到账）、`asset_sell`（卖出到账）、分红到账、借出的钱收回 | `liability_inflow` / `asset_inflow` | **资产 / 债务模块的收款记录**：放款到账与 `az_liability_loan_draw` 支取行、A3（借出的钱）收回行、卖出 / 分红到账对应的资产侧记录 |
| **两类都不算** | 转账、资产买卖、余额调整、K2 额度与欠款变动 | `transfer_out` / `transfer_in` / `asset_buy` / `credit_spend` / `interest` / `credit_repay` 的 `in` 那条 / `adjustment` / `opening` | `transfer` / `asset_buy` / `asset_sell` / `adjustment` / `debt_cost` / `statement`；**`credit_repay` 的 `in` 那条例外**，与出账腿同用 `liability_repay` + 同一个 `ref_id` | 各自模块或账户侧自身；`asset_buy` 指买入批次、`asset_sell` 指卖出批次 |

> 「资产 / 债务模块的**收款和还款记录**」就是上表后两行：收款＝放款到账、支取、收回、卖出与分红到账；还款＝贷款 / 分期还款附表那一条。**消费类直接连支出 / 收入模块，间接类连资产 / 债务模块**，不交叉。
>
> **关联分组 ≠ 统计分组**：`asset_buy` / `asset_sell` 在三个统计视图里「两类都不算」（形态转换、视图只取 `out`），但在关联侧各自指向资产模块批次；`asset_sell` 同时是间接入账，它的收款记录就是该卖出批次对应行。K2 的 `credit_repay / in` 同理：关联上共指同一条还款记录，统计上不单独进任何视图。

**六条约束**：

- **不加列**：`ref_type` / `ref_id` 两列 DDL 本来就可空，允许值在全局约定 3 列全即可；枚举仍不写 CHECK。
- **关联不决定统计**：三个视图只按 `entry_type` / `direction` / 账户 `kind` 取数，`ref_type` 空也能算总额。关联是给「点开一笔还款能看到是哪笔债」「点开一笔消费能看到哪张单据」用的，不给统计当筛子。
- **先有流水、后补单据**：支出 / 收入模块还没开工时 `ref_id` 留空，开工后按 `(ref_type, ref_id)` 回填或由新单据写入，**不强制 NOT NULL、不因此拒绝保存流水**。三个视图不受影响。
- **配对腿共指一条、只算一次**：信用卡还款那 2 条等值流水（K1 出账 + K2 入账）`ref_id` 指向**同一条还款记录**，但 K2 的 `direction='in'` 那条只是减欠款，不单独进任何统计视图，防双计。
- **两种配对别混**：`transfer_group_id` + `counterparty_account_id` 是**账户内部**两条流水互指（转账和信用卡还款都用），与 `ref_type` + `ref_id` 的**跨模块**指向是两码事；一笔流水可以同时有两者。
- **反查方向同样成立**：从债务还款附表 / 资产收款记录按 `(ref_type, ref_id)` 能反查到对应账户流水，靠已有索引，不另建视图表。

**入账侧暂不建统计视图**：三个视图只取 `direction='out'`。入账同样分组、同样关联，是为了以后要「这个月收了多少」「收回多少本金」时，直接按同一套直接 / 间接分组取 `in` 侧即可，不用重新设计字段。

## 一、主表 `accounts`（17 列）

```sql
CREATE TABLE IF NOT EXISTS accounts (
  id                    INTEGER PRIMARY KEY AUTOINCREMENT,
  book_id               TEXT    NOT NULL DEFAULT 'default',
  kind                  TEXT    NOT NULL,  -- liquid / credit / restricted / investment
  type                  TEXT    NOT NULL,  -- 四张形态清单，见全局约定 3；DDL 不锁
  name                  TEXT    NOT NULL,
  note                  TEXT    NOT NULL DEFAULT '',
  balance               TEXT    NOT NULL DEFAULT '0',  -- 累计值：K1/K3=余额，K2=已用额度，K4=剩余可用额；可为负
  initial_balance       TEXT    NOT NULL DEFAULT '0'
                        CHECK (CAST(initial_balance AS REAL) >= 0),
  is_liquid             INTEGER NOT NULL DEFAULT 1,  -- 计入「现在能花的钱」
  include_in_net_worth  INTEGER NOT NULL DEFAULT 1,  -- 计入「真正属于你的钱」
  sort_order            INTEGER NOT NULL DEFAULT 0,
  archived              INTEGER NOT NULL DEFAULT 0,
  deleted_at            INTEGER,
  delete_reason         TEXT,
  created_at            INTEGER NOT NULL,
  updated_at            INTEGER NOT NULL,
  revision              INTEGER NOT NULL DEFAULT 1,
  -- C7① 恢复：信用卡不计入「能花的钱」/「真正属于你的钱」，DDL 与 Controller 双保险
  CHECK (kind <> 'credit' OR (is_liquid = 0 AND include_in_net_worth = 0))
);

CREATE UNIQUE INDEX IF NOT EXISTS uq_accounts_active_name
  ON accounts (book_id, name) WHERE deleted_at IS NULL;

CREATE INDEX IF NOT EXISTS idx_accounts_list
  ON accounts (book_id, deleted_at, archived, kind, sort_order, id);
```

**累计值口径**：`balance` 一列四类共用，但**运算规则按类别分开**，共用一列不等于共用一条公式。

| 类别 | `balance` 是什么 | 恒等式 |
|---|---|---|
| K1 / K3 / **K4** | 当前余额 / **剩余可用额** | `期初 + Σ入 − Σ出`（储蓄类规则） |
| K2 | **已用额度（欠款）** | `Σ出 − Σ入`，**没有期初已用额度**（credit 规则取反） |
| 派生：可用额度 | 不建列 | `credit_limit − balance` |
| 当前未还 | 不建列 | **就是 `balance` 本身**（这张卡已用额度）。上期结转欠款 + 本期新增消费 − 本期已还款，由流水逐笔累加得出；挂卡分期剩余本金只是债务侧明细，不参与相加。**不建列，打开时现算** |
| 欠银行的钱 | 不建列 | `Σ balance WHERE kind='credit'` **+ Σ 贷款剩余本金 + Σ 不挂卡分期剩余本金**。信用卡那一项已经把挂卡分期的钱含在 `balance` 里了，分期行**不再另加**；「还能刷多少」是授信剩余，**不等于**当前未还，两者相加才等于总额度 |

**层级与引用约定**

- **主表** = `accounts`，`AUTOINCREMENT` 保证软删后 id 不复用，历史引用不指错账户。
- **次表** = **2 张**：`account_credit`（K2）、`account_investment`（K4）。K1 / K3 **没有次表**——不为对齐格式造空表（U1）。`account_id` 唯一指向主表 `id`，1:1。
- **附属表** = 3 张：`account_entries`（流水）、`account_category_bindings`（绑定用途）、`credit_card_rules`（信用卡章程）。
- **引用列分级**：账户侧流水与绑定按账户查询，**只带 `account_id`**；`credit_card_rules` 同样只带 `account_id`（**C3① 连带删掉 `sub_account_id`**，它从不参与查询）。不给流水表硬塞永远用不上的 `sub_account_id`。
- **次表 / 附属表骨架**：`id` 自增主键（次表）、`account_id`、留痕三件套。

**主表标注**

1. **四类一张表**。`kind` 决定去哪张次表（K1/K3 无次表），`type` 形态清单由 `allowedTypesFor(kind)` 唯一真源管控（下拉、保存校验、历史脏数据兜底都读它）。K2 清单不含通用「其他」，K3 清单不含任何信用形态，K4 清单只有 `stock_account`。
2. **单写点**：`balance` 唯一写入点 `AccountEntryDao.append`，一个事务内 insert 流水 + update 账户。编辑账户（改名 / 改额度 / 归档）把 `balance` / `initial_balance` 从 UPDATE 摘掉。**规则由调用方显式传 `AccountBalanceRule`**（无默认值，漏传编译不过），DAO 不读账户类别分叉。
3. **可为负**：4.7 余额不足也允许保存（橙色提示不拦），故 `balance` / `balance_after` 不加 `>= 0`；`amount` 仍严格 `> 0`（10.6）。
4. **部分唯一索引**：`WHERE deleted_at IS NULL` 让软删旧名不占名额；回收站 30 天后物理删行，`account_entries` **永远保留**（3.8）。删除前 `countEntries` 提示「还有 XX 笔记录」。
5. **归档 / 排序 / 回收站**：`archived=1` 不进日常列表但历史保留；`sort_order` 拖拽一次事务批量写；软删写 `deleted_at` + `delete_reason`，恢复置回 NULL。
6. **看板口径（3.6，C2 后按标志聚合而非按 kind 分栏）**：
   - **总资产取数**：按 `include_in_net_worth=1` 的账户余额聚合，**K4 投资账户并入并在看板单列**（与下方「投资账户单列」同源，不重复加）；信用卡「还能刷多少」是授信剩余，不加。**术语**：「流动资金账户（K1）」指账户类型；「储蓄类恒等式」指 K1/K3/K4 共用运算规则，两者不再混用「储蓄类账户」一个词。
   - 现在能花的钱 = `Σ balance WHERE is_liquid=1`（K4 的 `is_liquid` 恒 0，天然不进）
   - 暂时动不了的钱 = `Σ balance WHERE kind='restricted' AND include_in_net_worth=1`
   - **投资账户单列** = `Σ balance WHERE kind='investment'`（剩余可用额）+ 资产侧 A4 股票市值；市值不进账户表
   - 还能刷的额度 = `Σ (credit_limit − balance) WHERE kind='credit'`，单列并写「这不是你的钱，刷了就要还」
   - 欠银行的钱 = 上表「欠银行的钱」那一行（信用卡那项已含挂卡分期，不另加）
   - 界面**永不出现「资产 / 负债 / 净资产 / 现金流」**，一律大白话；金额颜色保持入账绿 / 出账红，符号只走 `MoneyFormat.signed`。
7. **A1/A2 只读镜像**：资产页顶部两块由本表现场聚合，账户是唯一写入点；归档 / 软删后镜像标「已断开」。账户侧不建镜像表、不存第二份余额。
8. **运行模型**：本表不产生「到点自动」的记录；所有变化由全局约定 7 的两个时机驱动。

**K2 标注**

1. 一笔信用卡一行；十项章程**一对一**挂在账户下。所有规则列允许「没填」：一项都不写照样能记消费与还款，只是不显示利息估算、不生成还款计划。
2. **只存不算**：本表存用户填的**规则**（静态参数）。本期该还多少、最低还多少、利息怎么算，都是**账户侧按本表章程现算**，不建「账单表」：办了分期的部分就是债务侧那行分期（挂卡号、有期数、逐期还），没办分期的部分钱一直挂在卡欠款里按日滚利息；花呗 / 白条归信用卡账户，同款处理。**最低还款不是分期行**（没有固定期数、不生成逐期记录），只对没办分期的那部分可用。不拿估算冒充银行账单，也不为这些结果另建表。**算与写的分工（契-13）**：打开时只算**展示值**（本期应还、最低还多少、按日滚利息一次性补算），不逐日生成流水、不落表；**账单出账动作**才把 I+F 写成**一次** `interest + debt_cost` 流水（全局约定 9）。信用卡不进负债表（C9-a），故无「负债侧按章程算金额」一说；贷款 / 分期的利息才由负债侧算。7.7 六种算法实现归信用卡计息模块，期间不生成假利息流水。账单出账那条 `interest` 只增加 K2 欠款、**不进三个统计视图**，息费在还款时随 `credit_repay` 计一次（全局约定 10）。
3. **余额口径**：主表 `balance` 是已用额度，`credit_limit` 是总额度，`available = credit_limit − balance` 永远算出来。信用卡 `is_liquid` 恒 0、`include_in_net_worth` 恒 0，界面单列「还能刷 X 元 —— 这不是你的钱，刷了就要还」。
4. **方向反着来**：消费是**出账**（`direction='out'`，已用额度 +），还款是**入账**（`direction='in'`，已用额度 −）。累计值增减由 `AccountBalanceRule.credit` 取反，**不与储蓄类复用公式**（3.2 / 3.4 / 10.9）。
5. **还款口径**按全局约定 9 落 **2 条等值流水**（储蓄出 + 信用卡入，金额 = 本金+利息+费用综合），**`interest=0` 不退化**；本息费在账单 / 负债附表拆，账户侧不拆成多条。还款金额不得超过当前已用额度（溢缴款属另一类业务）。`repay_account_id` 若填写必须是 K1 流动资金账户。
6. **还款提醒现算现显**：还款日提前 3 天，按 `due_day` + `balance` + `min_payment_rate` 现算「还有 3 天要还 X 元，将从 XX 卡扣款」。**只在用户填了 `daily_rate` 时才给利息粗估**，且标「估算，以账单为准」；没填就不编利息数（10.9）。提醒不落表、不预生成。
7. **方案 A 三列 · 本期消费额与归零**：
   - **真源是流水**：每笔 `credit_spend` 由 `AccountEntryDao.append` 写一条 `account_entries`；**同一事务内** `current_period_spent += amount`。列是「当期累计缓存」，不是第二真源（U2）。
   - **账单出账后清零**：按全局约定 7，只在用户打开 / 操作时判断「当前日期已跨过 `statement_day` 且 `last_period_key != 当前周期`」，满足才把 `current_period_spent` 与 `period_installed_amount` 归零、更新 `last_period_key`，**开始计算下期消费额**。**顺序关键：先滚动归零、再记本期消费**。归零只清这两列，不动负债侧任何数据（旧周期挂卡分期剩余本金仍在）。
   - `last_period_key` = 账单日所在自然月 `YYYY-MM`；31 号遇小月钳到月末；改账单日视为新周期（B13）。
   - **「按账单直接抄」降级为漏记补录校准**：用户发现少记几笔时，按账单差额补一条 `adjustment` 流水并同步该列；**退款 / 退货同样走流水**（负数以 `direction` 表达），不再「手动减一列」。若减后 `period_installed_amount > current_period_spent`，提示核对、**不自动撤销已办分期**（校验只在办分期那一刻做，事后不回溯，C6①）。
   - **办挂卡分期校验**（写入负债侧之前）：`installment_amount ≤ current_period_spent − period_installed_amount`；通过后 `period_installed_amount += installment_amount`。**校验在写入前做**。`mount_creditcard_id` 指向本卡即取本卡两列；不挂卡的商品 / 租金分期跳过校验。这条落实「不得对已办理分期的资金余额再次办理分期」。
   - **C6① 明写**：不校验分期资金来源、跨周期不追溯。
8. **契约①「挂卡分期不重复计」**：信用卡欠款只认主表 `balance` 一个数。办挂卡分期时**卡上欠款不动**（只是把其中一部分在债务侧挂了一行明细），每还一期卡上欠款减一次、债务侧那行剩余本金也减一次，**两边各记各的、永不相加**；总负债合计里挂卡分期不另加。例：额度 10000、刷 6000 办 6000 分期 → 卡上欠 6000、分期剩 6000，是同一笔钱；相加得 12000 就错了。
9. **契约③「花呗 / 白条归信用卡账户」**：`type='huabei'/'jiebei'` 落 K2，**不进负债表、不新增 `liability_type`、不新增资产类别**；账单分期按挂卡分期处理。借呗是现金贷（**放款到账**：账户侧一条入账 + 负债侧**同事务建一行 `az_liabilities`**，失败同滚；见契-11 / 流水标注 6），本草案只登记形态，不开放「借呗直接消费」入口。与 C9-a「建信用卡**不**建负债」并列：一个要求、一个禁止，链路都画全。
10. **生命周期**：账户软删 / 归档后次表与章程行保留，不物理删、不加外键级联（3.8 / 10.7）；`AUTOINCREMENT` 不复用 id，恢复后仍对得上。
11. **枚举不写 CHECK**：`interest_method` 现行代码写死 `CHECK IN ('','full','unpaid')`，本定稿去掉；`grace_amount` 从 `REAL` 改 `TEXT`（它是金额）。

### K4 `account_investment` 投资账户（股票账户）

```sql
CREATE TABLE IF NOT EXISTS account_investment (
  id               INTEGER PRIMARY KEY AUTOINCREMENT,
  account_id       INTEGER NOT NULL UNIQUE,  -- → accounts.id
  net_transfer_in  TEXT    NOT NULL DEFAULT '0',  -- 净转入额，**可为负**，不加 >= 0 约束
  created_at       INTEGER NOT NULL,
  updated_at       INTEGER NOT NULL,
  revision         INTEGER NOT NULL DEFAULT 1
);
```

**K4 标注**

1. **只有一列物理专属列**。剩余可用额 = 主表 `balance`，走**储蓄类恒等式**（K1/K3/K4 共用运算规则，与「流动资金账户」不是一回事；真实钱，不是授信）；股票市值由资产侧 A4 `az_asset_stock` 决定，**不进账户表**。「总额 = 股票市值 + 剩余可用额」在详情页现算，不物化、不成第二真源（A4 标注 305）。
2. **`net_transfer_in` 是净额，不是累计转入**：

   | 动作 | 净转入额 | 剩余可用额（`balance`） | 说明 |
   |---|---:|---:|---|
   | 从储蓄卡转入 1 万 ×3 | 3 万 | 3 万 | 两列都涨 |
   | 用 2 万买股票 | **3 万（不变）** | 1 万 | 买入扣款不减净转入额 |
   | 卖出到账 5 千 | **3 万（不变）** | 1.5 万 | **卖出到账不算转入** |
   | 转出 5 千到储蓄卡 | **2.5 万** | 1 万 | **转出时净转入额同步减少** |
   | 极端：从未转入、卖出到账 2 万后全额转出 | **−2 万** | 0 | 可为负：「每转出一笔相当于少转入了一笔」 |

3. **可为负的真实用例**再次印证 S1 的负号修正：净转入额、负余额、`balance_after`、A3 坏账 `total_gain` 都允许负。
4. **净转入额只作记录**：不参与任何加总、不算收益、不进看板、不推导「投入本金 / 盈亏」（收益由资产侧市值 + 现金流算，属分析模块）。账户侧**只记录、不推算**。
5. **`is_liquid=0`、`include_in_net_worth=1`**：`payableAccountsFor` 显式排除 K4（A8），它不是付款账户；但它的钱计入家底。**「投资账户 → 储蓄账户转出」照常能走**，C9-b 禁的只是「转账指向信用卡」。

#### K4 附：资金动作与流水（D2 定稿）

| 动作 | `entry_type` | `direction` | `ref_id` | `net_transfer_in` | `balance` |
|---|---|---|---|---|---|
| 储蓄卡转入投资账户 | `transfer_in` | `in` | — | `+amount` | `+amount` |
| 买入股票扣款 | `asset_buy` | `out` | → `az_asset_stock_buy` 批次 | 不变 | `−amount` |
| 卖出股票到账 | `asset_sell` | `in` | → `az_asset_stock_sell` 批次 | 不变 | `+amount` |
| 转出到储蓄卡 | `transfer_out` | `out` | — | `−amount` | `−amount` |

- **所有动作都写 `account_entries`**，走 `append` 单写点；转账类用 `transfer_group_id` 与对手账户成对，同一事务。
- **`net_transfer_in` 的唯一写入点也是 `append`**：在写 `transfer_in`（储蓄→投资）时 `+amount`、写 `transfer_out`（投资→储蓄）时 `−amount`，与 `balance` 更新、流水 insert **同一事务**完成；`asset_buy` / `asset_sell` 不改这一列。不允许单独 UPDATE 次表。
- **资产侧批次只记数量与价格，不重复记账户金额变动**；逐笔可用 `debit_account_id` 覆盖到 `liquid` 账户，主表 `link_account_id` 只作归集（资产草案全局约定 8 的 default 覆盖语义）。
- **`asset_buy` / `asset_sell` 是正式枚举值**（B3 显式分支），默认分支禁止兜底成 `liquid` / `opening`。
- **归档账户不能补记**：上述流水只在正常态产生，先恢复再记（S3 / 全局约定 7）。

```sql
CREATE INDEX IF NOT EXISTS idx_entries_account_type_time
  ON account_entries (account_id, entry_type, occurred_at);  -- 本期消费聚合 / 分类筛选
CREATE INDEX IF NOT EXISTS idx_entries_transfer
  ON account_entries (transfer_group_id);
CREATE INDEX IF NOT EXISTS idx_entries_ref
  ON account_entries (ref_type, ref_id);
```

**流水标注**

1. **一次变动一条流水，转账两条**：`transfer_group_id` 配对、`counterparty_account_id` 指对手，**不另建转账表**；两条 + 两个账户 `balance` 更新全在同一事务。
2. **两条恒等式**：储蓄类 `期初 + Σ入 − Σ出`（K1/K3/K4）；信用卡 `Σ出 − Σ入`（K2）。`direction` 只说钱往哪走，累计值增减由显式传入的 `AccountBalanceRule` 决定，**四类不复用同一公式**。
3. **金额恒正、符号只在展示层**：`amount` 严格 `> 0`（10.6）；界面「+ / −」只走 `MoneyFormat.signed`；入账绿 / 出账红保持语义色。
4. **逐笔时点快照**：`balance_after` / `credit_limit_after` 由 `append` **在同一事务**读账户当前值后覆盖写入，调用方不传。**B2 写入路径**：`append` 按 `rule` 分路——储蓄类只读主表 `balance`；**K2 在同一事务 JOIN `account_credit` 取 `credit_limit`**（格式为 TEXT，经 `Money.parse` 转 `int`）。新建信用卡 = 主表 + `account_credit` **同事务写入**，否则首笔消费前 JOIN 取不到额度。K4 不参与额度读取，`credit_limit_after` 恒 NULL。
5. **余额调整**：`adjustment` 时 `reason` 必填；改余额本身也留流水。
6. **还款 2 条等值流水**（C9-c / 全局约定 9）：信用卡还款 = 储蓄卡一条 `credit_repay` 出账 + 信用卡一条 `credit_repay` 入账，金额严格相等（= 本金+利息+费用综合），同事务、用 `transfer_group_id` 配对；账户侧**不拆 `principal_part` / `interest_part` 两列、不新增枚举值**，`interest=0` 不退化。本息费在账单 / 负债附表拆，支出统计按 `entry_type` 分组取数、不依赖 `ref_type`（全局约定 10）。
   **三类还款通用**：信用卡还款、分期还款、贷款还款执行还款动作时，**付款那张卡都留一条出账记录**，记清金额、时间、还的是哪笔债（`ref_type` + `ref_id` 指过去）；不加表、不加流水类型。此处「一视同仁」**只指都要留付款卡出账记录，不指流水条数、不指实现复用**（契-10② C9-b 仍生效）。**挂卡分期每还一期**：由负债页还款动作**同事务触发账户侧 `append` 写 2 条等值 `credit_repay` 流水**减 `accounts.balance`，负债侧同时改当期 / 生成下一条 `pending` / 减 `remaining_principal`；不写这一步则 `balance` 永不下降、总负债永久高估（契-1）。债务侧「总亏损」只做这笔债维度展示，**账户流水与债务侧总亏损不相加**，否则同一笔利息双计。
   **借呗放款**：账户侧一条入账 + 负债侧**同事务建一行 `az_liabilities`**，失败同滚。
   **其它资金动作**：放款 / 借钱到账写一条入账；基金买入选「扣款」写出账、选「不扣」按**历史持仓补录**处理（契-14，不写账户流水）；卖出 / 分红到账写入账、选「不到账」同样按补录处理。
7. **三个统计视图的取数**（全局约定 10）：先限定「非 K2 存储账户」且 `direction='out'`，再按 `entry_type` 分消费类 / 还款类两组；**生活成本 = 消费类**、**实际支出 = 消费类 + 还款类**、**资产抵消 = 还款类**，金额取 `amount` 全额、不分本息。`credit_spend` 与账单出账 `interest` 动的是 K2 额度与欠款，**不进三个视图**；同一笔钱只在还款月由 `credit_repay` 计一次，不双计；转账、资产买卖、余额调整两类都不算。取数不依赖 `ref_type`，`ref_type='debt_cost'` 只作界面标签。三个视图只取 `direction='out'`；**入账记录同样分直接 / 间接两组，并与出账一样关联业务单据**，见全局约定 11。净资产恒等验算见全局约定 9，与本节不是同一口径。
8. **`record_source`**：`user` = 用户主动记；`auto` = **仅**软件在**账单出账动作**里自动带出的息费那条（`entry_type='interest'` + `ref_type='debt_cost'`）。转账两条、还款两条都 `user`（B13）。**不是**定时生成的计划。
9. **真分页与筛选**：`occurred_at DESC, id DESC` 倒序，`limit + offset` 下推 SQLite；「全部 / 出账 / 入账」只对 `direction` 过滤，与账户类别无关。分页状态唯一真源在 Controller，不进表。
10. **使用频次由流水聚合**：`GROUP BY account_id` 取 `COUNT(*)` / `MAX(occurred_at)`，**不冗余 `last_used_at` / `use_count`**。记支出模块未开发时 `ref_type` 全 NULL，按品类 / 单据过滤需等该模块开工；**三个统计视图不依赖 `ref_type`**（全局约定 10），启用过滤无需改表。
11. **恒等式审计**：`auditBalance` 返回「应有累计值 − 实际 `balance`」；审计是**读**路径可按 `kind` 推规则，`append` 是**写**路径必须显式传，不矛盾。
12. **跨模块关联**（全局约定 11）：用已有 `ref_type` + `ref_id` 把流水指到业务单据，**不加列、不建中间表**。消费类出账 → 未来支出模块支出记录；直接入账 → 收入模块收入记录；还款类出账 → 债务模块还款记录；间接入账（放款到账 / 收回 / 卖出 / 分红）→ 资产 / 债务模块收款记录。转账与信用卡还款那 2 条的**账户内部配对**仍走 `transfer_group_id` + `counterparty_account_id`，与跨模块指向互不替代；配对的两条 `ref_id` 共指同一条还款记录，但 K2 入账那条不单独进任何统计视图。`ref_id` 可空、未来模块开工后回填，三个视图不依赖它取数。

### 3.2 绑定用途表 `account_category_bindings`（3.5 多对多，软约束）

```sql
CREATE TABLE IF NOT EXISTS account_category_bindings (
  account_id   INTEGER NOT NULL,  -- → accounts.id
  category_id  INTEGER NOT NULL,  -- → 支出分类 id
  created_at   INTEGER NOT NULL,
  updated_at   INTEGER NOT NULL,
  revision     INTEGER NOT NULL DEFAULT 1,

CREATE INDEX IF NOT EXISTS idx_bindings_category
  ON account_category_bindings (category_id, account_id);
```

1. 「不能随便花」≠「完全不能花」：勾几个支出类型 = 「这个账户的钱只许花在这些地方」；一个类型可被多个受限账户绑定，故用关联表而非主表 JSON。

3. **社保三道锁**、**公积金可绑定**、`liquid_locked=1` 强制 `is_liquid=0` 且开关禁用（全局约定 8）。
4. **A2 只读镜像**：用户改账户，镜像跟着看；不允许在资产页反改余额；删 / 归档后标「已断开」。

## 四、实现口径补充

1. **形态清单唯一真源**：`allowedTypesFor(kind)` 四张清单写死在业务层（K1 / K2 / K3 / K4 互不相交），下拉、保存校验、历史脏数据兜底全读它；DDL 不锁 `type`。**历史脏数据兜底回退到该类别默认形态**，不把错配值塞进候选首位。
2. **B2 写入路径（阻断级补漏）**：主表已无 `credit_limit`，`append` 必须按 `rule` 分路并 JOIN `account_credit`；`AccountRecord.availableCredit` / `subtitle` / 最低还款估算 / `statsFor` 的取数随之改联表。K4 次表不参与 `append` 的额度读取。
3. **B3 枚举兜底**：四个 `fromDb` 显式分支 + 默认 `unspecified` / 抛错；禁止 `_ => liquid` / `_ => opening`。
4. **不建的表清单**：转账表（`transfer_group_id`）、**信用卡账单表**（本期应还 / 最低还款 / 利息都打开时现算，不落表）、月末快照表（归分析 13.12）、使用次数表（聚合）、变更历史 JSON 表（全局 `change_log`）、镜像表（只读派生）、股票账户独立表（K4 次表已建）、自动创建的对应负债表（C9-a）。
5. **状态列清单**：`is_liquid` / `include_in_net_worth` / `liquid_locked` / `archived` / `non_binding` / `sort_order` / `period_installed_amount` / `current_period_spent` / `last_period_key` / `net_transfer_in`，均为「详情阶段用或软件重算」，**新增时不填**（除默认值）。
6. **C7① 四条跨列业务一致性 CHECK 原样恢复**（只去枚举取值 CHECK）：主表 `kind <> 'credit' OR (is_liquid=0 AND include_in_net_worth=0)`；流水表 `adjustment → reason 非空`、转账两条必须同时有 `transfer_group_id` + `counterparty_account_id`、`opening` 只能是 `in`。**这四条是跨列约束，不是数值范围约束**；`amount > 0` / `initial_balance >= 0` / 比例 `0~1` / 天数 `1~31` 属数值范围 CHECK，一直在 DDL 里，无需「恢复」。现行 `CreditCardAccountController.save` 已显式写 `isLiquid:false / includeInNetWorth:false`，恢复 DDL 后回到「DDL + Controller 双保险」。
7. **B10 循环利息入口 / 账单出账动作**（契-13）：用户打开 / 操作时按 `last_period_key` 判跨账单日，**账户侧**按 `credit_card_rules` 现算本期息费（`daily_rate` / `interest_method` / 7.7 算法，打开时只算展示值），**账单出账时写一条** `interest` + `debt_cost` 出账流水（全局约定 7 / 9，不定时生成、不逐日补流水）。信用卡不进负债表（C9-a），故**无「负债侧算金额」一说**；贷款 / 分期的利息才由负债侧算。
8. **全库一次性重建**（B12）：两份草案文首各写一条；禁止分模块先后重建，避免 `link_account_id` 悬空。
9. **B15 四项补漏**：
   - **`book_id` 一致性**：流水 `book_id` **必须取该账户的 `book_id`**，由 `append` 写入，不取默认值；否则 `idx_entries_book_time` 按账本统计会串。
   - **删除 `availableCredit` 的 null 兜底**：`credit_limit` 为 `NOT NULL CHECK > 0`，业务必填、DDL 亦必填；现行「额度为空返回 null、界面显示 —」分支删除。
   - **索引补齐**：`account_credit(statement_day)` 供打开时跨账单日扫描；`account_entries(account_id, entry_type, occurred_at)` 供本期消费聚合与分类筛选，两条已写入 DDL。
   - **章程表 upsert 语义**：`credit_card_rules` 补了 `created_at` 后，`upsert` 不得再用 `conflictAlgorithm: replace` 全量覆盖；**保留 `created_at`、只更新业务列并递增 `revision`**。
10. **版本与旧数据**：账户侧 4 张旧表全删、不做迁移（全局约定 1）；现行 v4→v9 迁移脚本随旧表一起废弃。开发期若仍保留旧库，B 延后期间三条纪律照旧。
11. **独立 SQL 文件导出、按实现方视角重排章节**属可选项，不影响表结构。

## 五、与资产 / 负债 / 分析模块的边界

| 对方 | 怎么连 | 谁写 |
|---|---|---|
| 资产主表 `az_assets.link_account_id` | 单向指向 `accounts.id`：这项资产绑定哪张卡（买股票 / 买房从哪扣） | 资产侧写，账户侧只读 |
| A4 股票 `az_asset_stock` | 市值 / 持仓数量与价格；**K4 次表不重复记** | 资产侧写 |
| A5 基金 / A6 别的投资 | `default_account_id` 指向**流动资金账户（K1）**，不建 K4 形态 | 资产侧写 |
| A1 / A2 只读镜像 | 由 `accounts` 现场聚合，**不落库、不缓存** | 账户侧唯一写入点 |
| 负债主表 `az_liabilities.link_account_id` | 单向指向 `accounts.id`：用哪张卡还这笔债 | 负债侧写 |
| 分期次表 `mount_creditcard_id` | 单向指向 K2 信用卡，只标记「这笔分期是哪张卡分出来的」；卡上欠款与分期剩余本金是同一笔钱、各记各的不相加，分期行不进总负债合计 | 负债侧写，账户侧只读卡号 |
| **当期分期额**（A6） | 从**负债侧**查：`Σ az_liability_installment_repay` 当期 `pending` 记录的 `principal_part + interest_part + fee`；账户侧只有累计量、查不出本期增量，**不另算一份** | 负债侧读，账户侧不写 |
| **借钱的成本**（C8① / 契-12） | **账户流水是三个统计视图的唯一真源**（取数见全局约定 10 / 流水标注 7）：按 `entry_type` 分消费类 / 还款类两组，还款类金额含息费、全额计；`ref_type='debt_cost'` 只作界面标签「借钱的成本」，账单出账 `interest` 那条不单独计一次支出；**贷款 / 分期**靠 `ref_id` 指向 `az_liability_loan_repay.id` / 分期还款附表对应行，**债务侧 `total_loss` 只做这一笔债维度展示、与三个视图不相加**；**信用卡不进负债表**（C9-a），账单出账息费无负债侧行，`ref_id` 可空或指账单周期标识，不走对齐。三个视图只按 `entry_type` 取数，不依赖记支出模块开工 | 账户侧写流水，负债侧只展示 |
| A4 股票持仓 vs 可用额 | **持仓市值 / 数量 / 价格**在资产侧 `az_asset_stock`；**剩余可用额 = 主表 `accounts.balance`**（复用，不物化第二份余额），K4 次表**另存** `net_transfer_in`；**两者各记各的、不相加**，「总额 = 股票市值 + 剩余可用额」详情页现算（契-15） | 资产侧 / 账户侧各写各的 |
| 月末快照（13.12 / 8.1.3 / 8.1.4） | 按月末存一次数、锁定历史；**归分析模块** | 账户侧不建表、不自动写 |
| 情境设计（8.2 / 13.2 / 13.11） | 月收入、每月必须花的钱、通胀、能撑几个月、应急金 | **参数只在情境设计录入一次，账户侧不存副本、不计算、不展示推演结论** |
| **出入账与业务单据的关联**（全局约定 11） | **出账、入账对称**，都用已有 `ref_type + ref_id` 指到业务单据，**不加列、不建中间表**：消费类出账 → 支出模块支出记录；直接入账 → 收入模块收入记录；还款类出账 → 债务模块还款记录（`az_liability_loan_repay.id` / 分期还款附表）；间接入账（放款到账 / 支取 / 借出的钱收回 / 卖出 / 分红到账）→ 资产 / 债务模块收款记录。两列可空，模块未开工不阻塞流水；三个视图按 `entry_type` 取数、不依赖关联 | 账户侧写 `ref_type` / `ref_id`，各模块写自己的单据 |
| 记支出 / 记收入 | 业务单据外挂 `ref_type + ref_id`；「非绑定用途」破例 | 各模块写单据，账户侧只留流水 |
| 历史持仓补录（契-14） | 开发 / 上线时用户已买入 → 直接创建基金或资产，**不走账户扣款、不写账户流水**，只在资产侧生成记录；属「新建」但明确不产生账户流水、不产生债务待办记录，补录持仓不参与资金变动校验 | 资产侧写，账户侧 0 条 |
| K4 双值不相加（契-15） | 剩余可用额 `balance` 与净转入额 `net_transfer_in` 各记各的；卖出到账 / 买入扣款不改净额，储蓄↔K4 转入转出同增减两项，净额可为负 | 账户侧写 |

界面口径：账户页永不出现「资产 / 负债 / 净资产 / 现金流」；「真正属于你的钱」按 10.9 一次减完；「欠银行的钱」「借进来的钱」「借出去的钱」只看不额外加减。

### 8.2 全库唯一核心接口（IF-01~IF-10）

##### IF-01 `UnitOfWork.run`

```text
/// 【所属模块】service/core · 业务事务编排
/// 【实现功能】全库唯一业务事务入口：把多个功能接口的 SQL 放进同一个 txn，任一步失败整体回滚，提交成功后才执行 afterCommit
/// 【使用限制】所有写动作必须经此入口；DAO 与功能接口第一参数统一收 DatabaseExecutor、不自建事务；嵌套调用经 Zone 复用同一 txn、不新开事务；database_shell 建表事务是 Schema 装配，不参与业务组合；与页面无关
/// 【入参与结果】必填 callback(DatabaseExecutor txn)；选填 afterCommit / onRollback 回调；返回 Future<T>，必须 await；结果只作为业务返回值，不得用于刷新挂事务内、不得写回 balance
/// 【异常与调用方处理】callback 内任一 DAO / CHECK / 文件 IO 异常原样上抛，最外层整体回滚并执行 onRollback（删新落盘文件）；调用方自行 try/catch 提示用户、保持旧快照、不得吞异常后继续；异常时 afterCommit 一律不执行
```

- **功能描述**：把"债务处理 + 账户出账"这类跨接口组合收口到一个事务；这是硬-19「后者失败应回滚前者」的可验证落点。
- **逻辑描述**：开 `txn` → 依次执行 callback（各接口共享同一 `DatabaseExecutor`）→ 全部成功则 commit → 执行 `afterCommit`（刷新两侧快照 / 通知 / 删旧图）；任一步抛错则 rollback → 执行 `onRollback`。图片文件 IO 不纳入 SQLite 事务，由 IF-09 两阶段补偿。
- **限制描述**：全库 `db.transaction` 仅此 1 处业务入口（另 1 处是 `database_shell` 建表）；禁止在接口内部自行 `db.transaction`；禁止事务内 `refresh` / `notifyListeners` 把未提交中间态推给页面。
- **应用描述**：契-1「还一期挂卡分期同事务触发 2 条等值 `credit_repay`」、契-11「三类还款付款卡都留出账」、契-18「`markPlanPaidIn` 与 `ledger.debit` 同处一个 `run`」、分类「软删 + 压平顺序」、全局约定 9「`append` 同事务累加三列」全部由它编排；时序见 8.4。

##### IF-02 `EntityKind`

```text
/// 【所属模块】service/core · 实体登记
/// 【实现功能】登记全库实体类型与职责：四类账户、A3~A11 资产、贷款/分期、流水 entry_type；新增实体只在此加一行
/// 【使用限制】只读登记，无 DB 写副作用；不放业务规则、不认识页面；新增实体时不得在别处另建一份清单
/// 【入参与结果】按实体键查询；返回不可变的种类描述（含 allowedTypesFor(kind) 等派生），同步返回、无需 await；结果用于分派次表 / 校验形态 / 枚举兜底，不得当作可写状态
/// 【异常与调用方处理】未知键抛 ArgumentError/StateError；由调用方自行 catch 并回退到「该类别默认形态」或直接拒绝保存；不抛异常的路径也要在注释中写明，禁止 _ => liquid / _ => opening 式兜底（B3）
```

##### IF-07 `AccountEntryDao.append`

```text
/// 【所属模块】database/account · 账户流水单写点
/// 【实现功能】流水与累计值唯一写入点：同一事务 insert account_entries + update accounts.balance，并写 balance_after / credit_limit_after 逐笔快照
/// 【使用限制】全库调用点仅 1 处且在 AccountLedger 门面；业务层禁止直调；只收 DatabaseExecutor、不自建事务；规则由调用方显式传 AccountBalanceRule（无默认值，漏传编译不过），DAO 不读账户类别分叉
/// 【入参与结果】必填 txn、accountId、direction、amount、entryType、occurredAt、rule；其余列按 entryType 配套；返回 int entryId，必须 await；balance_after 由 DAO 读账户当前值覆盖写入，调用方不传、不得用返回值反写 balance
/// 【异常与调用方处理】DAO/CHECK 异常（amount>0、adjustment→reason 非空、transfer 两条必须有 transfer_group_id+counterparty_account_id、opening 只能 in）原样上抛，与同事务其他 UPDATE 一并回滚；由 UnitOfWork 统一处理，调用方不得吞异常后继续
```

- **功能描述**：单写点原则的物理落点——`balance` 唯一写入点；编辑账户把 `balance` / `initial_balance` 从 UPDATE 摘掉。

- **应用描述**：全局约定 7「一次事务成组处理」、全局约定 9 还款 2 条等值、方案 A 三列同事务累加、K4 四类资金动作；对应主表标注 2、流水标注 4、四节第 2 条。

### 8.4 跨模块编排与事务示例（契-1 / 契-11 / 契-12 / 契-18）

**示例一：负债页「还一期挂卡分期」**（IF-10 + IF-Z16 + IF-A08 + IF-01）

```text
UnitOfWork.run((txn) async {
  // ① 债务侧：markPlanPaidIn —— 当期改「已还」、填 remaining_after、生成下一条 pending、减 remaining_principal
  final plan = await azWrite.markPlanPaidIn(txn, ...);
  // ② 账户侧：同事务触发 2 条等值 credit_repay 流水（储蓄出 + 信用卡入），减 accounts.balance
  await ledger.repay(txn, creditAccountId, repayAccountId, plan.amount, ...);
}, afterCommit: () { refreshLiability(); refreshAccount(); });
```

- **为什么必须同事务**：不写 ② 则 `accounts.balance` 永不下降、总负债永久高估（契-1）；② 任一步抛错，① 已执行的 UPDATE 必须一并撤销（硬-19）。
- **不双计**：卡上欠款与分期剩余本金是同一笔钱，**各减一次、永不相加**；分期行不进总负债合计；债务侧 `total_loss` 只做这一笔债维度展示，与账户三个统计视图靠 `ref_id` 对齐、**不相加**。
- **刷新时机**：两侧 `refresh` 只挂 `afterCommit`，禁止在事务内 `notifyListeners`。

**示例二：三类还款付款卡都留出账**（契-11）：信用卡还款走 IF-A08（2 条等值）；分期 / 贷款还款走 IF-10（付款卡 1 条出账 + 债务处理同事务）；三者 `entry_type` 都用 `credit_repay` 出账腿、`ref_type='liability_repay'` + `ref_id` 指向对应还款记录，但**「一视同仁」只指都要留付款卡出账记录，不指流水条数、不指实现复用**（C9-b 仍生效）。

**示例三：借呗放款**（契-11）：账户侧一条入账（IF-06）+ 负债侧**同事务建一行 `az_liabilities`**，失败同滚；与 C9-a「建信用卡不建负债」并列登记，一个要求、一个禁止。

**示例四：历史持仓补录**（契-14）：IF-Z08 只在资产侧生成记录，**0 条账户流水、0 条债务待办**，不参与资金变动校验、不倒推扣款、不报错；是有意的期初事实录入，账本从这一刻起以此为起点。之后正常买入选「扣款」才写 `asset_buy`，卖出 / 分红选「到账」才写入账。

**示例五：分类「软删 + 压平顺序」与图片提交**（契-18）：前者同事务；后者文件 IO 非 DB 级原子，用 IF-09 `plan.commit()` / `plan.discard()` 补偿做到最终一致。
