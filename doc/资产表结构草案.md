### 全局约定

**1. 旧表处置**：**本模块前缀（`az_*`）的原有表全部删除，以本文档新表为准**；账户模块及其他既有模块的表由各自模块文档单独处置，本文档不删除、不迁移、不改名。不做旧数据迁移；如需留存本模块历史数据，另走一次性导出。本文档所有表名即本模块当前版本的最终表名。
>
> **全库一次性重建（执行契约）**：两份草案各自处置自己前缀 **≠** 可分两次重建。本模块 `az_assets.link_account_id` / `az_liabilities.link_account_id` 单向指向 `accounts.id`，**物理交付必须全库一次性重建，禁止分模块先后执行**，否则留下静默悬空引用。

**2. 金额与价格一律用 `TEXT` 存十进制字符串**，不用 `REAL` 浮点，避免精度丢失与末期强制归零时的尾差。数值范围校验统一写 `CHECK (CAST(列名 AS REAL) > 0 / >= 0)`；默认值写 `DEFAULT '0'`。文档里的金额示例（10000、833.33、9200 等）一律以**元**叙述，落库直接存同值字符串，不需要 ×100。**利率、费率、比例、周期数值、数量**仍用 `REAL` 小数（5% 写 `0.05`、20% 写 `0.2`），它们不是金额，不受本条约束。计算统一走**全库唯一** `Money` 工具类（`parse(String) → int` 分 / `format(int) → String`，加减全用 `int`、内部禁用 `double`，见《项目规范与契约.md》要-6b），**不引第三方 Decimal 依赖**；禁止浮点直接累加。本条为全库唯一计算契约，账户侧与资产侧共用同一份实现。

**3. 枚举规则**：**所有枚举列都不写 CHECK**，但每列注释里写明允许值，并在下面这张总表列全，由业务层校验取值。

**6. 易混字段释义**（英文字段对应到业务里到底是什么，避免只给列名对不上）：

| 字段 | 在哪 | 业务含义 | 谁填 |
|---|---|---|---|
| `annual_rate` | 分期次表 | **年利率**，5% 写 `0.05`。有息计费填，免息计费留空 / 0；软件用它算利息，写附表 `interest_part` | 用户录入 |
| `per_term_fee_rate` | 分期次表 | **每期手续费率**，5% 写 `0.05`。软件用它算「每期手续费」，写附表 `fee` | 用户录入 |
| `fee` | 两张还款附表 | **本期费用**。贷款侧＝用户还款时填的额外费用（账户管理费、担保费等）；分期侧＝只由 `per_term_fee_rate` 算出的手续费 / 提前结清时算出的剩余手续费 | 贷款：用户还款时填；分期：软件算 |

| `settle_rule` | 分期附表 | **提前结清规则名**，不是金额。存用户结清时选的规则（免收未出账 / 收齐剩余各期 / 只加收一期 / 按剩余本金比例 / 另收服务费），软件据此算剩余手续费 | 用户结清时选 |
| `settle_rule_ratio` / `settle_service_fee` | 分期附表 | **规则输入值**。前者存「按剩余本金比例」的比例，后者存「另收一笔服务费」的金额；只各服务于对应规则 | 用户结清时填 |
| `remaining_after` | 两张还款附表 | **这一期还完后还剩多少本金**。生成 `pending` 时留空，执行还款动作算出后才填；该值同时是次表 `remaining_principal` 和下一条记录的「还前剩余本金」 | 软件在还款时算 |

**7. 运行模型：记录只能在「新建」和「执行还款动作」时生成（最高优先级约束）**

**软件在用户不打开应用的时候不处理任何数据**。用户可能一天打开一次，也可能一个月都不打开，不存在「到点自动跑」这回事。因此：

- **所有记录只在两个时机产生**：①用户新建一笔资产 / 债务时，软件生成**第一条**待办记录；②用户执行还款动作时，软件算出结果、写回当前记录、再生成**下一条**记录。除此之外不生成任何记录。
- **禁止定时生成**（「每月 1 号自动生成下月利息」不成立）、**禁止一次生成全部计划**（「签约一次排 N 条」不成立）。未来永远只有**一条** `pending` 记录。
- **只能循环 / 递归处理**：用户一次补足多期逾期款时，软件按「还当前这条 → 生成下一条 → 用余额继续还 → 再生成下一条」逐条推进，直到余额用完或余额归零。具体递归式见主表标注 4、贷款附表标注 3、分期附表标注 8。
- **打开应用时按需补齐状态**：逾期、罚息、应还日判断都在用户打开 / 操作时现算现标，不依赖后台定时任务跨天累计。
- **这条约束是普遍的**：凡遇到「谁生成下一条」「什么时候生成」「要不要一次排完」「逾期多期怎么补」这类问题，一律按本条处理。适用位置：A3（借出的钱）月息表标注 2/5、贷款次表标注 3、分期次表标注 5、逾期状态机、清偿顺序。

**8. 账户绑定口径**：**跨类按账户统计一律取主表 `az_assets.link_account_id`**，它是资产唯一绑定的账户。A5（基金）次表 `default_account_id`、A6（别的投资）次表 `account_id` 保留为「默认操作账户」，只服务于该类逐笔买入 / 卖出 / 分红时覆盖用（`debit_account_id` / `credit_account_id`）；A4（股票）直接用主表列、不另设。三层并存是**default 覆盖**语义，不是三套独立绑定，实现方按主表列汇总即可，不必改表。

**9. 分期计费与结清**：分期次表有 `annual_rate`——**利率算的归 `interest_part`（利息）、费率算的归 `fee`（手续费），两列各归各**；免息计费＝没有利息、只有手续费（`annual_rate` 空 / 0），有息计费＝既有利息又有手续费，判定只看 `annual_rate` 有没有值，不另建「计费类型」列。提前结清规则的输入值存 `settle_rule_ratio` / `settle_service_fee`；分期还款时用户先选「是否提前结清」、选「是」再选规则，软件按规则验证金额（见第六节标注 7）。

## 一、主表 `az_assets`（15 列）

```sql
CREATE TABLE IF NOT EXISTS az_assets (
  id               INTEGER PRIMARY KEY AUTOINCREMENT,
  book_id          TEXT    NOT NULL DEFAULT 'default',
  asset_class      TEXT    NOT NULL,  -- A3~A11，决定去哪张次表
  name             TEXT    NOT NULL,
  icon_key         TEXT    NOT NULL DEFAULT 'other',
  note             TEXT    NOT NULL DEFAULT '',
  total_gain       TEXT    NOT NULL DEFAULT '0',  -- 总收益（收益值，不是收入值；收益值 = 收入值 − 成本值），各类公用
  link_account_id  INTEGER,
  sort_order       INTEGER NOT NULL DEFAULT 0,
  archived         INTEGER NOT NULL DEFAULT 0,  -- 允许值：0/1（0=否，1=是）
  deleted_at       INTEGER,
  delete_reason    TEXT,
  created_at       INTEGER NOT NULL,
  updated_at       INTEGER NOT NULL,
  revision         INTEGER NOT NULL DEFAULT 1
);

CREATE UNIQUE INDEX IF NOT EXISTS uq_az_assets_active_name
  ON az_assets (book_id, name) WHERE deleted_at IS NULL;

CREATE INDEX IF NOT EXISTS idx_az_assets_list
  ON az_assets (book_id, deleted_at, asset_class, sort_order, id);
```

**总收益口径**：`total_gain` 存的是**收益值**，不是收入值；通用定义是「收益值 = 收入值 − 成本值」。**通用定义只是口径说明，各类以下面这张表为准**——A7（房产）/ A8（车辆）的成本走负债侧、不在本表扣，A9（贵重物）按自己的收入成本公式。

| 类型 | 总收益怎么算 |
|---|---|
| A3（借出的钱） | 确认收回 + 待还本金 − 借出金额 = **累计已收利息**（阶段收益；全部还完即最终收益）。**坏账时改为：确认收回 − 借出本金，可为负** |
| A4（股票）/ A5（基金） | **总收益 = 确认收入 + 成本价 × 当前数量 − 总成本**。确认收入 = 已卖出部分收入之和（单次卖出收入 = 卖出价 × 数量 − 手续费）；成本价 = 单次买入的 `(买入价 × 数量 + 手续费) / 数量`，多批次取加权平均；总成本 = 所有买入成本之和。逐笔联动公式见 A4 / A5 标注 |
| A6（别的投资） | 收入金额 − 投入金额（次表不再存收益，写主表） |
| A7（房产）/ A8（车辆） | **出租收入就是收益**。成本（支出）由房贷 / 车贷在负债侧体现；**当前估值不能作为收益的确认项**——它无法短期兑现、且存在浮动，不讨论增值贬值带来的利益影响，只算这项资产直接带来的收益 |
| A9（贵重物） | **总收益 = 确认收入 − 已售部分成本**（已实现收益，与 A4/A5 同尺子）。卖出时按批次结转已售成本，`total_cost` 只留剩余持仓成本；未卖出部分按成本计、不计浮动盈亏。逐笔口径见 A9 业务标注 |
| A10（生意） | 过程只看收益记录表（分红收益）；权益卖出时 = 卖出金额 + 分红总额 − 投入成本 |
| A11（其他） | 期间收益均为 0；归档时按成本与最终价值计算 |

**层级与引用约定**

- **主表** = `az_assets`，主键 `id`。
- **次表** = 各分类的资产记录表，共 9 张。`asset_id` 唯一指向主表 `id`，自身主键 `id`。
- **附属表** = 各分类下的其他表（月息、还款、买卖、分红、出租、收益记录、卖出分摊等），共 16 张。每张必须同时保存 `asset_id`（→ 主表 `id`）和 `sub_asset_id`（→ 对应次表 `id`）两列。

**引用列**：16 张资产附属表统一带 `asset_id`（→ 主表 `id`）与 `sub_asset_id`（→ 对应次表 `id`）双引用，与负债侧附表一致。

**次表统一骨架**：`id` 自增主键、`asset_id` 关联主表且唯一（一项资产一行，1:1）、`created_at` / `updated_at` / `revision` 留痕。每张次表字段分成「数据（新增录入）」和「状态（详情阶段用，新增不填）」两组。

**附属表留痕**：16 张资产附属表统一带 `created_at` / `updated_at` / `revision` 三件套，与次表、负债侧附表一致。

## 二、九张次表

### A3 `az_asset_loan` 借出的钱

```sql
CREATE TABLE IF NOT EXISTS az_asset_loan (
  id             INTEGER PRIMARY KEY AUTOINCREMENT,
  asset_id       INTEGER NOT NULL UNIQUE,
  -- 数据：新增录入
  amount    TEXT    NOT NULL CHECK (CAST(amount AS REAL) > 0),  -- 借了多少
  repaid_amount      TEXT    NOT NULL DEFAULT '0' CHECK (CAST(repaid_amount AS REAL) >= 0),  -- 已还金额
  confirmed_repaid   TEXT    NOT NULL DEFAULT '0' CHECK (CAST(confirmed_repaid AS REAL) >= 0),  -- 确认收回：借款人累计已实际还回、且确认到账的全部钱（本金部分+利息部分）= Σ(principal_part+interest_part)；定义见标注 6
  lent_at        INTEGER,  -- 哪天借
  due_at         INTEGER,  -- 说好什么时候还，可空
  has_interest   INTEGER NOT NULL DEFAULT 0,  -- 是否计息，新增时选；允许值：0/1（0=否，1=是）
  annual_rate    REAL    CHECK (annual_rate IS NULL OR annual_rate >= 0),  -- 年利率，5% 写 0.05；不计息留空
  voucher_note   TEXT    NOT NULL DEFAULT '',  -- 借条 / 转账凭证
  -- 状态：详情阶段用，新增不填
  repay_state    TEXT    NOT NULL DEFAULT 'normal',  -- 正常/部分收回/已收回/可能收不回
  created_at     INTEGER NOT NULL,
  updated_at     INTEGER NOT NULL,
  revision       INTEGER NOT NULL DEFAULT 1
);
```

#### A3 附：借款月息表、还款记录表 + 业务标注

```sql
CREATE TABLE IF NOT EXISTS az_asset_loan_interest (
```

**标注**

1. 新增借款时，`repay_state` 就是「正常」（表里的默认值 `normal`）。收没收回、收不收得回，是详情页以后的事。
2. 「是否计息」选「是」时，年利率必填；**新建借款时**软件往月息表写一条**第一条**利息，状态默认「未生效」。
   利息 = （借了多少 − 已还金额）× 年利率 ÷ 12，生成时算定存进 `amount`。
   **生成时机按全局约定 7**：不按月定时生成、不一次排满全年；**只有「新建」和「用户执行还款动作」这两个时机会产生下一条**。用户一个月不打开，那一个月的月息记录不会凭空出现，等他打开 / 还款时再按当前剩余本金递推补上。
3. 到 `due_at` 那天，这条利息从「未生效」转「待还」；还掉了转「已还」。这个状态变化也只在**用户打开 / 操作时**判定并写入，不靠后台跨天累计。
4. 还剩多少不再存表，由 `amount − repaid_amount` 算出。收到的利息**不冲减本金**。
5. 还款分两种，每还一次往还款记录表写一条：
   - **还本金**：只累加 `repaid_amount`，`interest_part` 为 0；往期利息记录一概不动、状态原样；**执行本次还款动作后**，软件按新的剩余本金算好并生成**下一条**月息记录（全局约定 7，不是定时排好等在那儿）。
   - **还本息**：先把往期利息逐条清成「已还」，这部分记进本笔 `interest_part`；剩下的钱累加进 `repaid_amount` 和 `principal_part`；同样在本次还款动作后生成下一条。

   熟人无息借款直接用「还本金」；外人有息借款用「还本息」，把利息先结清。
6. **【确认收回】的定义**：`confirmed_repaid` = **截至当前，借款人已经实际还回来、且用户确认到账的全部钱，含「本金部分」和「利息部分」**，等于 A3（借出的钱）还款记录表 `az_asset_loan_repay` 里所有记录 `principal_part + interest_part` 的累计。
   - 它和 `repaid_amount`（**只记已还本金**）不是同一笔：`confirmed_repaid = repaid_amount + 累计已收利息`。
   - 对应标注 5 两种还款：**还本金**只累加 `repaid_amount`、`interest_part = 0`；**还本息**先把往期利息清成「已还」记进 `interest_part`，剩下的钱累加 `repaid_amount` 和 `principal_part`——两种都天然等于「本笔实际到账的钱」，所以逐笔累加即可，不需要用户另填。
   - **为什么必须是这个定义**：标注 6 的总收益公式是「确认收回 + 待还本金 − 借出金额」。把定义代入：`(已还本金 + 已收利息) + (amount − 已还本金) − amount = 累计已收利息`。也就是说，**总收益 = 累计已收利息**：有息借款赚的就是收到的利息，无息借款为 0，本金收回只是资产形态从「借出的钱」变回现金、不算收益。若把「确认收回」理解成「只含利息」或「只含本金」，公式都会算出负数或恒为 0，与账单不符——这是唯一能让公式自洽的解释。
   - **总收益**：`total_gain` = 确认收回 + 待还本金 − 借出金额 = **累计已收利息**。待还本金 = `amount − repaid_amount`，借出金额 = `amount`。
   - **阶段收益与最终收益**：已得利息就是**阶段收益**——每还一次、`confirmed_repaid` 涨一次，累计已收利息就是到此刻为止的收益；**全部还完后，所有已得利息就是最终收益**。本金从来不计入收益，只是资产形态变化。
   - **由软件计算**：`confirmed_repaid` 由软件按 `az_asset_loan_repay` 逐笔累加写入、`total_gain` 由软件按上式算好写主表，**用户不手填这两列**。
   - **坏账**：用户把 `repay_state` 标为「**可能收不回**」（即坏账）时，不再按上面的阶段收益口径，改为 **`total_gain = 确认收回 − 借出本金`**，**收益可以为负**（收不回的部分就是亏损）。坏账不另建核销金额 / 日期列，标记本身即触发这个公式；主表 `total_gain` 是 `TEXT`、没有 `>= 0` 约束，天然可为负。

- 股票账户：新增股票时**必须绑定一个股票账户**；绑定关系用主表已有的 `link_account_id`，A4 表不另加账户字段。买入时从该账户扣款，卖出记录也归在同一账户下。
- 账户类型：账户侧已**单独建一类「投资账户」**，只给股票用（券商资金卡），表结构见《账户表结构草案.md》，本模块不再标注待建。它记的是「真实还剩多少钱能买股票」，与信用卡「还能欠多少」方向相反；主表 `balance` 复用为剩余可用额，另有一张小表记净转入额。基金 / 别的投资**不建这一类**，买卖默认走储蓄类账户。
- 是否扣款：新增股票 / 首笔买入时给一个「是否扣款」选择。选「是」→ 从绑定股票账户的剩余可用额扣掉本次要扣的钱；选「否」→ 只记这笔买入，不扣任何账户。这是录入时的动作开关，不写进表。
- 一笔卖出可能挂多笔买入，所以单独用 `az_asset_stock_sell_fill` 记「从哪笔买入消耗了多少」；按买入时间**从早到晚**依次消耗（先买先卖），每消耗一笔就减那笔买入的 `remaining_quantity`、刷新 `sell_state`。
- 分红方式决定有没有现金：`10派1元` 有现金，`10转3股` / `10送3股` 没有（`dividend_cash = 0`）。**送转股必须联动持股数**：软件从 `dividend_method` 文本里解析「每 10 股转 / 送 X 股」，按当时 `total_quantity` 算出增加股数，写入 `az_asset_stock.total_quantity`；**总成本不变，成本价按新数量摊薄**（`cost_price = total_cost / total_quantity`）。这样「成本价 × 当前数量」才不会与总成本对不上。不新增列，股数变化由这条分红记录留痕。
- **成本、收入、总收益的逐笔联动（软件维护次表两列，用户不手填）**：
  - **单次买入成本** = `买入价 × 买入数量 + 手续费`（即 `az_asset_stock_buy.buy_price × buy_quantity + buy_fee`）。**成本价** = 本次成本 / 本次数量 = `(买入价 × 数量 + 手续费) / 数量`；多批次买入时次表 `cost_price` 取**加权平均成本价** = `总成本 / 总买入数量`。
  - **总成本** `total_cost` = **所有买入记录的成本之和**，每次买入累加一次。
  - **单次卖出收入** = `卖出价 × 卖出数量 − 手续费`（`az_asset_stock_sell.sell_price × sell_quantity − sell_fee`）。**确认收入** `confirmed_income` = **已卖出部分的收入之和**，每次卖出累加一次；`az_asset_stock_sell_fill` 记录该笔卖出从哪些买入批次消耗了多少，先买先卖。
  - **总收益** = **确认收入 + 成本价 × 当前数量 − 总成本**，算出后写主表 `total_gain`。当前数量 = `total_quantity`（买入累加、卖出扣减）。
    - 含义：总成本 = 剩余持仓成本 + 已售部分成本，所以上式等价于「已实现收益」，**未卖出部分按成本价计、不计浮动盈亏**，与全文「不讨论增值贬值」一致；全部卖光时 = 全部卖出收入 − 全部买入成本。
    - 分红现金（`az_asset_stock_dividend.dividend_cash`）按同一口径**并入确认收入**（现金分红是已到手的收入）；送转股只改数量、不产生收入。
  - `total_commission` / `total_stamp_tax` / `total_dividend_tax` 是费用明细的累计展示，**手续费已经含在成本价和卖出收入里**，总收益公式不再单独减一次，避免重复计。
  - 这几列由软件在**买入 / 卖出动作发生时**按上式写回，用户不手填；两列随交易逐笔累加，默认 `'0'` 只表示尚无交易。

- 一笔卖出可挂多笔买入，用 `az_asset_fund_sell_fill` 记分摊；按买入记录的 `created_at` **从早到晚**依次消耗。
- 分红记净值前后、金额、到账账户，**并区分现金分红与份额再投**：现金分红时 `dividend_amount` 并入确认收入、份额不变；**份额再投**时不产生现金，按 `新增份额 = dividend_amount / nav_after` 累加进次表 `quantity`，`total_cost` 同步加这笔再投金额（等价于一次新买入），成本净值按 `总成本 / 总份额` 重算。区分方式由录入时的动作开关给定，不写进表；记录本身留在 `az_asset_fund_dividend`，可回溯。
- **成本、收入、总收益的逐笔联动（软件维护次表两列，用户不手填）**：
  - **基金与股票的区别只在买入侧**：股票是「按价 × 数量下单」，基金是**买入时指定金额**，软件按手续费率 `buy_fee_rate` 和买入净值 `buy_nav` 反算份额：`手续费 = 买入金额 × 费率`，`买入份额 = (买入金额 − 手续费) / 买入净值`，写入 `az_asset_fund_buy.buy_quantity`。
  - **基金的成本更好算：买多少钱，成本就是多少**。`总成本 total_cost` = **所有买入金额之和**，每次买入累加一次（不按净值再折算一遍）；`cost_nav` 是成本净值 = `总成本 / 总份额` 的展示值。
  - **单次卖出收入** = `卖出净值 × 卖出数量 − 赎回费`（`az_asset_fund_sell.sell_nav × sell_quantity − redemption_fee`）。**确认收入 `confirmed_income`** = 已卖出部分收入之和，每次卖出累加一次；`az_asset_fund_sell_fill` 按买入记录 `created_at` 从早到晚分摊。
  - **总收益 = 确认收入 + 成本净值 × 当前份额 − 总成本**，算出后写主表 `total_gain`（与 A4（股票）同一把尺子，只是「成本价 × 数量」换成「成本净值 × 份额」）。分红金额 `az_asset_fund_dividend.dividend_amount` 并入确认收入；`total_redemption_fee` 是赎回费累计展示，已含在卖出收入里，不再单独减。
  - 同 A4（股票）：这几列由软件在买入 / 卖出时按上式写回，用户不手填；默认 `'0'` 只表示尚无交易。

2. 使用方式为「出租」时，生成**下个月**的一条出租记录，状态「待到账」。这条租金到账、标成「已到账」后，再生成下个月的记录——始终只留一条未到账的。

5. **抵押状态保留二值、不表示押了几次**：`mortgage_state` 只有「未抵押 / 已抵押」，默认「未抵押」，由负债绑定驱动、不在新增里填。它是**派生值**：只要存在至少一笔 `has_collateral = 1` 且未结清的贷款（`az_liability_loan.link_asset_id` 指向本房产）→ 「已抵押」；这类负债全部清除后 → 回「未抵押」。**同一房产被抵押多少次、是哪几笔，不在这个字段里表达，也不建顺位字段/多押列表**。

   - **新增**一笔以该资产为抵押品的贷款（`has_collateral = 1` 且 `link_asset_id` 指向本资产）时 → 把本资产 `mortgage_state` 同步改为「已抵押」；

   **小列表弹窗**：资产详情页点开抵押信息时，实时反查 `az_liability_loan WHERE link_asset_id = 本资产 id AND has_collateral = 1`，列出**所有**指向该资产的抵押贷款（含已结清的，带状态标签），每笔显示 `name`（主表 `az_liabilities.name`）、剩余本金 `remaining_principal`、主表 `status`；**已软删的不列**。弹窗只做展示、不落库、不存快照；「押了几次」看这个列表，不进 `mortgage_state`。
   **与负债侧的分工**：负债表允许多笔贷款指向同一资产（**每笔各一行**，见第五节标注 7），资产侧只显示「有没有被押」；登记顺位、登记生效/对抗、拍卖分配、差额转普通债权、解押状态一概不记。
6. **总收益**：房产的**收入就是总收益**——已到账的按月出租记录 + 空置收益记录里的金额合计，写主表 `total_gain`。成本（支出）由房贷在负债侧体现，不在本表扣。**当前估值不能作为收益的确认项**：它无法短期兑现、且存在浮动，所以不讨论房产增值贬值带来的利益影响，只算这项资产直接带来的收益。`current_value` 只服务总资产统计，与 `total_gain` 无关，**由用户录入、软件不自动更新**：新增时必填，一时没有估值就先填买入价，之后用户手动改；全文「不讨论增值贬值」指的就是这个字段不参与收益计算，不是说不能存。

```sql
  ON az_asset_business_income_record (asset_id, occurred_at);
```

**标注**

1. 投入金额、所占比例**至少填一个**：金额投资填投入金额；技术投资投入金额可填 0 或空，但必须给所占比例。

5. 「至少填一个」是录入时的业务规则，没写进表约束。
6. **总收益**：过程**只看收益记录表**，合计写主表 `total_gain`；当前估值不参与。`amount` 允许正负：**正数**记分红 / 卖出回款，**负数**记按份额承担的亏损或追加投入，零分红不记记录。**权益卖出的「卖出金额」不单列字段**，就用这张收益记录表写一条正数记录承载（金额 = 实收卖出款），因此权益卖出后的总收益仍是 `Σ收益记录 amount − 投入成本`，公式不变、也不需要新建卖出表。

## 四、负债侧：主表 `az_liabilities`

> 跟资产一样分三级：债务记录作主表、每种类型作次表、类型下的表作附表。主表见本节；贷款次表 + 还款附表 + **支取记录表**见第五节，分期次表 + 还款附表见第六节，共 6 张表。
> 表名 `az_liabilities` 即最终结构；原表处置见文首全局约定 1。

```sql
CREATE TABLE IF NOT EXISTS az_liabilities (
  id               INTEGER PRIMARY KEY AUTOINCREMENT,
  book_id          TEXT    NOT NULL DEFAULT 'default',  -- 账本分组，当前恒 'default'
  liability_type   TEXT    NOT NULL,  -- 贷款 / 分期；信用卡不进负债表

-- 与资产主表对称：同账本下未软删的债务名字唯一
CREATE UNIQUE INDEX IF NOT EXISTS uq_az_liabilities_active_name
  ON az_liabilities (book_id, name) WHERE deleted_at IS NULL;

-- 列表/筛选：账本 + 软删 + 类型 + 排序
CREATE INDEX IF NOT EXISTS idx_az_liabilities_list
  ON az_liabilities (book_id, deleted_at, liability_type, sort_order, id);
```

**主表标注**

1. 一笔欠款一行；`liability_type` 只有**贷款 / 分期**两个值。信用卡不在这建、不在这改、不在这看，创建与详情都在账户部分。
2. 主表**不放债务余额**：剩余本金等归次表。`total_loss` 是累计亏损统计值，不是余额。总负债统计口径 = `Σ 贷款剩余本金 + Σ 信用卡账户当前未还 + Σ 不挂卡分期剩余本金`。**「信用卡账户当前未还」就是那张卡的已用额度（账户主表 `balance`）本身**，办分期时这笔钱不走、每还一期两边各减一次；**信用卡分期**（`mount_creditcard_id` 非空）的剩余本金是同一笔钱在债务侧的明细，只作明细、**不与卡上欠款相加、不进合计**，否则翻倍。**不挂卡的商品 / 租金分期**（且**不挂任何信用账户**）没有账户汇总兜底，是用户实际支出只是滞后了，剩余本金单独进合计；花呗 / 白条一类已按覆-03 归信用卡账户，属挂卡分期、不在此项（主表标注 7）。
   **账户侧契约（已定稿对齐）**：账户侧表结构见《账户表结构草案.md》，已按下面三句逐条核对；三句是——① **挂卡分期不重复计**：卡上欠款与分期剩余本金是同一笔钱，各记各的、不相加，分期行不进合计；② 储蓄账户余额计入总资产、且不计算收息（覆-01，主表标注 7）；③ 花呗 / 白条归信用卡账户、按挂卡分期处理（覆-03，主表标注 7）。账户侧已按主表标注 8 定稿（稿件）「本期新增消费额」三列与办分期前校验，见《账户表结构草案.md》。
3. `total_loss`（总亏损）= **所有亏损的和**：利息 + 费用 + 违约金（提前还款违约金）**+ 放款时先扣的服务费 `service_fee`**。服务费算亏损的理由很简单：合同借 10000、先扣 800 服务费、到手 9200，那 800 是用户额外背上的负担，不是还款，计入亏损。逐期来源见贷款附表标注 5；**分期没有放款，不计 `service_fee` 这一项**，其口径见第六节附表标注 5。逐期金额均由软件按各次表参数计算后写入附表，`total_loss` 由软件累加，**不需要用户手填**。 **`total_loss` 只做这一笔债的维度展示，不进账户侧「这个月花了多少」的支出统计**；账户流水是支出唯一真源（利息那条是出账流水 + 「借钱的成本」标记，`ref_id` 指向本笔 `az_liability_loan_repay.id` / 分期还款附表对应行），两处靠 `ref_id` 对齐、不相加，否则同一笔利息算两遍（见《账户表结构草案.md》第五节「借钱的成本」、《项目规范与契约.md》契-12）。
4. `status` 新增即「正常」（`normal`）。枚举不写 CHECK，取值由业务层管。**与附表 `state` 的联动**：
   - 某期还款记录过 `due_at` 未还 → 该记录 `state` 改「逾期」，**主表 `status` 同步改「逾期」**；
   - 这条逾期记录**还款前不生成下一条**还款记录；
   - 还款后生成下一条并做计算；若新记录的 `due_at` 已过（生成时当前时间已晚于应还日）→ 它也直接标「逾期」、按时间算罚息，主表保持「逾期」，继续不生成再下一条；
   - **直到某次生成的下一条待还记录是正常「未还（`pending`）」状态，主表 `status` 才标回「正常」**；
   - 逾期罚息按「罚息 + 复利」算，写附表 `penalty_amount`，**计入主表 `total_loss`**——这是用户在整笔债务里操作导致的实际支出，不是账面数字；具体公式与依据见贷款附表标注 3「逾期计息口径」。全部还完则主表 `status` 改「已结清」。两张还款附表同用这套状态机（见第五节附表标注 3、第六节附表标注 8）。
   - **一次补足多期＝递归处理**：用户一次还一大笔把好几期逾期款都补上时，软件按下面的式子**逐条循环**，不是合并成一条、也不是后台一次排完：
     ```
     本次还款额 R
     当前这条逾期记录：先扣「本次还款记录额」+「逾期费用」（罚息 + 复利）
     余额 = R − 本次还款记录额 − 逾期费用
     余额 > 0 → 生成下一条还款记录（按状态机判定它是否也逾期），用余额继续还它，重复本步
     余额 = 0 → 停
     ```
     即「还当前这条 → 生成下一条 → 用余额还下一条 → 再生成下一条 …」依次类推，直到余额用完；每条该标逾期就标逾期、该算罚息就按时间算罚息、`remaining_principal` 逐条递减。**这就是清偿顺序**：先清当前这条的本息 + 逾期费用，剩下的才轮到下一条，不需要另定「费用→利息→本金→违约金」的扣划顺序。
   - **为什么只能是循环（全局约定 7）**：软件在用户**不打开应用时不处理任何数据**，用户可能一天打开一次、也可能一个月不打开，所以记录**只能在「新建」和「执行还款动作」这两个时机生成**——定时生成不成立、一次生成全部计划不成立。逾期状态、罚息天数也在用户打开 / 操作那一刻现算现标。今后凡属「谁生成下一条 / 什么时候生成 / 一次补多期怎么算」这类问题，一律按本条与全局约定 7 处理，**不再单列为待定项**。
5. 贷款类的**起止时间**分两类：`start_date` 一律必填；**按期还款类**的 `end_date` **界面禁用手动修改，值由 `start_date + total_terms × term_unit` 计算得到后存入该列**（算出存入、界面禁用手改）；**一次性还清 / 随借随还类**没有总期数，`end_date` 由用户自己填且**业务上必填**，同样存入该列（不再允许留空，否则按占用天数计息没有终点）。L3（贷款首期不足一整期后延）顺延、I6（分期缩期）重推，都是**重算后写回这一列**。主表 DDL 这两列仍可空，是为了兼容两类贷款的不同规则和分期；「必填 / 禁用 / 可编辑 / 由公式推并写入」全在录入层做，没写进表约束。分期的起止时间见第六节标注 4。
6. **合同号 / 订单号与平台特殊场景**：放贷机构、合同号、分期订单号 / 商户**不单列字段**，写进主表 `name` / `note` 或该笔还款记录 `note`；混合贷拆成的公积金 / 商贷两笔用 `name` 区分（如「房贷-公积金」「房贷-商贷」）。分期被平台**提前终止、剩余本金一次性计入账单**时，仍按全额提前结清流程走，但**允许按平台账单金额人工覆盖**（`manual_adjusted = 1`），由软件在 `note` 记「平台终止 + 账单金额」作为来源，不强求用户先选 `settle_rule`。
7. **账户侧归类**：
   - **覆-01 储蓄账户**：现金 / 活期 / 余额宝 / 货币基金一律归**储蓄账户**（账户侧的「流动资金账户」），**不新增资产类别、不改 `az_assets.asset_class` 枚举**。**放弃收息计算**——活期利息、余额宝收益不计，不建利息记录、不算收益，这类账户不适用 `total_gain`。余额**由用户自己走「账户余额变更」手动改**，不天天改、软件不自动同步、不接银行 / 支付平台流水；账户侧已落地：每次改余额写一条调整流水。**总资产按 `include_in_net_worth=1` 的账户余额聚合，K4 投资账户（券商资金账户里的真钱）并入并在看板单列**（已定稿（稿件），见《账户表结构草案.md》主表标注 6 / 第七节契约②）；信用卡「还能刷多少」是授信剩余、不是自己的钱，不加。**术语**：此处「储蓄账户」指 K1「流动资金账户」，「储蓄类恒等式」指 K1/K3/K4 共用运算规则。
   - **覆-03 花呗 / 白条**：一律归**信用卡账户**（循环额度），**不进负债表、不新增 `liability_type`、不新增资产类别**。它们的账单分期按**挂卡分期**处理：`mount_creditcard_id` 只指向该信用卡账户，卡上欠款与分期剩余本金各记各的、不相加，**分期行不进总负债合计**，与信用卡分期完全同款。
   - **I1 边界**：「电商分期按不挂卡进合计」只适用于**真正不挂任何信用账户的商品 / 租金分期**；花呗白条这类挂信用账户的归账户侧，不计入 `Σ 不挂卡分期剩余本金`。
   - 账户侧四类账户（流动资金 / 信用卡 / 其他资金 / 投资账户）**已全部定稿**，表结构见《账户表结构草案.md》，本文档不建账户表。
8. **「当期使用额度」与当期分期额从哪查**（账户侧已落地，见《账户表结构草案.md》）：

   **先说清几个「额度」各是什么、哪些根本不建列**：

   | 说法 | 是什么 | 存不存 |
   |---|---|---|
   | 总额度 `credit_limit` | 这张卡最多能刷多少 | 存，信用卡专属表 |
   | 已用额度 / 卡上欠款 | 现在一共欠多少 | **不另建列**，就是账户主表 `balance`（信用卡上取反算） |
   | 可用额度 | 还能刷多少 = 总额度 − 已用额度 | **不建列**，打开时算 |
   | 当前未还 | 这张卡现在欠多少 | **不建列**，就等于已用额度（`balance`）本身 |
   | 当期使用额度 `current_period_spent` | 本账单周期新刷了多少 | 存，信用卡专属表 |
   | 本期已办分期额 `period_installed_amount` | 本周期已经拿多少消费办了分期 | 存，信用卡专属表 |

   `used_amount` / `available` / `current_unpaid` **都不建成列**，理由统一：凡能由已有列现算出来的数，不另存一份。已用额度就是 `balance`，再建一列是同一份数存两处；可用额度是减法，存了就得在每次消费、还款、调额时同步改三处；当前未还也是 `balance` 本身，而软件在用户不打开时不处理数据，存列反而会留过期值。账户侧「流水是唯一写入点」，多一个可写的累计列就多一处会对不上的地方。

   **额度推演（把最容易混的几个时刻钉死，额度 10000）**：

   > **本账本口径**：下表「办分期不释放额度、每还一期释放一期」是本项目记账口径，与银行 App 显示可能不同；不照抄银行事实，结论不改（R3）。

   | 时刻 | 已用额度 | 可用额度 | 当期使用额度 | 分期剩余本金 |
   |---|---:|---:|---:|---:|
   | 刷了 6000 | 6000 | 4000 | 6000 | — |
   | 拿这 6000 办半年期分期 | **6000** | **4000** | **6000（不是 0）** | 6000 |
   | 还首期本金 1000 | 5000 | 5000 | 见下 | 5000 |
   | 跨账单日后又刷 1000 | 6000 | 4000 | **1000** | 5000 |

   - **办分期不清零当期使用额度、也不释放额度**。当期使用额度记的是「这期刷了多少」，跟这 6000 后来变成普通欠款还是分期无关；办分期不产生消费流水、不产生还款流水，所以三列累计量全都不动。它只在**账单日出账**时归零。
   - **还款也不减当期使用额度**。还款不是消费，不写消费流水；上面「还首期后当期使用额度变成 1000」的前提是**已经跨过账单日、先滚动归零再记新消费**，不是还款动作减掉的。顺序永远是「先归零、再记本期消费」。
   - **当前未还 ≠ 可用额度**，方向是反的：当前未还 = 已用额度 = 6000，可用额度 = 10000 − 6000 = 4000，两者相加才等于总额度。它等于「上期结转欠款 + 本期新增消费 − 本期已还款」由流水逐笔累加出来的 `balance`，**不再把分期剩余本金加一遍**（那是同一笔钱，加了就翻倍）。
   - **每还一期，卡上欠款减一次、债务侧那行剩余本金也减一次**，两边同步、各记各的；分期行只当明细看。**触发链（契-1）**：用户在负债页执行「还一期分期」→ **同事务触发账户侧 `append` 写 2 条等值 `credit_repay` 流水**（储蓄出 + 信用卡入）减 `accounts.balance`，负债侧同时改当期 / 生成下一条 `pending` / 减 `remaining_principal`；不写这一步则 `balance` 永不下降、总负债永久高估。

   **当期分期额从负债侧查**：`Σ az_liability_installment_repay` 里当期 `state='pending'` 的 `principal_part + interest_part + fee`；每笔分期独立一行，多笔相加进同一张账单。各笔剩余本金取次表 `remaining_principal`。账户侧只有累计量、查不出本期增量，不另算一份。

   **方案 A（已落地）**：信用卡专属表含三列——`current_period_spent TEXT NOT NULL DEFAULT '0'`、`period_installed_amount TEXT NOT NULL DEFAULT '0'`、`last_period_key TEXT`（上次归零所属周期，如 `'2026-03'`），金额一律 TEXT。**真源是每笔消费流水**：每刷一笔写一条流水，同一事务内累加当期使用额度；那三列只是当期累计缓存，不是第二份真源。**不另建「消费流水表」**——账户侧本来就有统一的 `account_entries`，不重复造。

   **账单周期与归零**：周期由账单日界定。**不做定时归零**——按全局约定 7，软件不打开时不处理数据；只在**用户打开 / 操作时**判断「当前日期已跨过账单日且 `last_period_key != 当前周期`」，满足才把两列归零并更新 `last_period_key`。**顺序关键：先滚动归零、再记本期消费**，否则新消费会被误清。归零**只清这两列，不动负债侧任何数据**——旧周期的挂卡分期剩余本金仍在（实跑验证：跨周期后合计仍 13000）。

   **校验公式（办挂卡分期时，写入负债侧之前）**：`installment_amount ≤ current_period_spent − period_installed_amount`；通过后写分期行，并 `period_installed_amount += installment_amount`。**校验在写入前做**。`mount_creditcard_id` 指向该卡即取该卡两列；**不挂卡的商品 / 租金分期跳过校验**；花呗 / 白条归信用卡账户后同样适用。这条从数据上落实「不得对已办理分期的资金余额再次办理分期」。

   **漏记、退款怎么记**：用户发现少记几笔时，按账单差额**补一条校准流水**并同步当期使用额度（不是「按账单直接抄」当真源）；**退款 / 退货同样走一条流水**，不手改那个数。若减后 `period_installed_amount > current_period_spent`，**提示用户核对、不自动撤销已办分期**——校验只在办分期那一刻做，事后不回溯。

   **A 不校验什么**：不校验分期金额对应的是哪笔具体消费（那是方案 B 才有的能力），只保证「金额不超过本期还没分过期的消费额」。

   **三类还款通用**：信用卡还款、分期还款、贷款还款执行还款动作时，**付款那张储蓄卡 / 存储卡写一条出账记录**，记清金额、时间、还的是哪笔债；三者一视同仁，不加表、不加流水类型。账户流水是「这个月花了多少」的唯一真源，债务侧 `total_loss` **只做这笔债维度的展示**，两边靠关联 id 对齐、**不相加**，否则同一笔利息双计。

   实跑验证（额度 50000）：周期 1 消费 5000 → 办 5000 分期通过、同周期再填 3000 被拦；用户 4/20 打开 → 先滚动归零、再记消费 8000 → 办 8000 分期通过、超额 12000 被拦；两期当期分期额 = 863.33 + 1381.33 = **2244.66**（负债侧可查）；归零后挂卡分期剩余本金合计 13000 不受影响。基础数字：办分期那一刻可用仍 **45000**，还完第 1 期可用 **45833.33**。详见《账户侧归类定稿与信用卡分期额度验证.md》。

## 五、负债侧：贷款次表 `az_liability_loan`

```sql
CREATE TABLE IF NOT EXISTS az_liability_loan (
  id                    INTEGER PRIMARY KEY AUTOINCREMENT,
  liability_id          INTEGER NOT NULL UNIQUE,  -- → az_liabilities.id（主表主键）
  -- 数据：新增录入
  loan_amount            TEXT   NOT NULL CHECK (CAST(loan_amount AS REAL) > 0),  -- 贷款金额（合同本金）
  actual_received_amount TEXT   CHECK (actual_received_amount IS NULL OR CAST(actual_received_amount AS REAL) >= 0),  -- 实际到账金额，先扣服务费时小于合同本金
  service_fee            TEXT   NOT NULL DEFAULT '0' CHECK (CAST(service_fee AS REAL) >= 0),  -- 服务费（放款时先扣的那笔，计入主表 total_loss 亏损）
  remaining_principal    TEXT   NOT NULL CHECK (CAST(remaining_principal AS REAL) >= 0),  -- 剩余待还（待还本金）
  repay_method           TEXT   NOT NULL,  -- 允许值：equal_principal(等额本金)/equal_installment(等额本息)/interest_first(先息后本)/lump_sum(一次性还清)/revolving(随借随还)；封闭枚举：等额本金 / 等额本息 / 先息后本 / 一次性还清 / 随借随还；软件按取值选用不同公式计算每期
  annual_rate            REAL   CHECK (annual_rate IS NULL OR annual_rate >= 0),  -- 年利率，5% 写 0.05；软件按 term_unit 折算成期利率用于计算
  overdue_penalty_rate   REAL   NOT NULL DEFAULT 0 CHECK (overdue_penalty_rate >= 0),  -- 逾期罚息率（年化，合同载明的罚息利率，常为合同利率上浮 30%~50%，不是正常年利率），9% 写 0.09；软件按「逾期本金 × 率/365 × 逾期天数」算罚息，并对到期应付未付的期内利息按同率计复利
  repay_day              INTEGER,  -- 还款日：按月/季/年时填「每期第几号」；day/week 留空（due_at 由起始日按单位顺推，见标注 5）
  paid_terms             INTEGER NOT NULL DEFAULT 0,  -- 已还期数
  total_terms            INTEGER,  -- 总期数
  term_unit              TEXT   DEFAULT 'month',  -- 期数单位：day/week/month/quarter/year，默认月；无固定期数显式写 NULL。day=每 N 天、week=每周六、month/quarter/year=每月固定几号；见标注 5
  prepay_penalty_rate    REAL   NOT NULL DEFAULT 0 CHECK (prepay_penalty_rate >= 0),  -- 提前还款违约金率，5% 写 0.05；软件按「提前还本金额 × 率」计算，逐笔记在附表
  has_collateral         INTEGER NOT NULL DEFAULT 0,  -- 是否有抵押；允许值：0/1（0=否，1=是）
  link_asset_id          INTEGER,  -- 抵押资产 → az_assets.id；多笔贷款可指同一资产
  created_at             INTEGER NOT NULL,
  updated_at             INTEGER NOT NULL,
  revision               INTEGER NOT NULL DEFAULT 1
);
```

**标注**

1. 一笔贷款一行，`liability_id` 唯一指向主表。金额关系 **`loan_amount = actual_received_amount + service_fee`**：录入只填 `loan_amount`（合同本金）和 `service_fee`（默认 0），`actual_received_amount`（实际到账）**禁用填写**，由 `loan_amount − service_fee` 计算得到。服务费默认 0 时 `loan_amount = actual_received_amount`。例：合同 10000、服务费 800 → 实际到账算得 9200。`remaining_principal` 是现在还欠多少，还一次改一次。
2. **`repay_method` 是封闭枚举**，只能是这五个值（允许值写在列注释和文首全局约定 3，**不写 CHECK**、由业务层校验），每个值各自对应**不同的还款安排与利息计算方式**，业务层按取值走不同生成 / 计息逻辑：

   | 值 | 中文 | 归组 |
   |---|---|---|
   | `equal_principal` | 等额本金 | 按期还款类 |
   | `equal_installment` | 等额本息 | 按期还款类 |
   | `interest_first` | 先息后本 | 按期还款类 |
   | `lump_sum` | 一次性还清 | 一次性还清类 |
   | `revolving` | 随借随还 | 一次性还清类 |

   归组决定软件按哪种节奏生成还款计划（见附表标注 1），取值本身决定软件用哪套公式算每期金额（标注 3）。**分类不另存字段**，直接看 `repay_method` 是哪个值就知道属哪组——五个值本身已经把分组说清了，再存一遍会多一份要同步的状态。**枚举不写 CHECK**，五个允许值连同中文含义写在列注释和文首全局约定 3，由业务层校验取值；`status` / `state` 等其余枚举同样处理。
3. **还款计算由软件完成**。五个值不是五种债务，一笔贷款仍一行；但**每个值对应一套不同的计算公式**。用户新增贷款、填好次表数据后，软件按 `repay_method` 算好每期本金 / 利息，写入附表并生成**下一期待还（`pending`）**记录；用户**不自己生成、不填这些金额**。**两个不预填的例外**：`fee`（本期费用）由用户在还款时填写（次表没有费用率，见标注 10）；`remaining_after`（还完后剩余本金）在生成 `pending` 时留空，执行还款动作算出后才填（见标注 15）。各参数取值如下。

   - **计算输入**：`loan_amount`、`annual_rate`、`total_terms`、`term_unit`、`repay_method`、`repay_day`、`prepay_penalty_rate`、`overdue_penalty_rate`。
   - **期利率**：`month → annual_rate/12`、`quarter → /4`、`year → 原值`；**日利率 = `annual_rate/365`，周利率 = 日利率 × 7**。依据：央行 2026 年《人民币存贷款利率管理规定（征求意见稿）》拟把存贷款计息基准由 360 天统一为自然年实际天数（平年 365、闰年 366），旧合同常见 `日利率=年利率/360、周利率=年利率/360×7`（广发、渤海合同），两种基准并存；本项目按新规方向 + 你的兜底取 365，旧合同差异走人工调整（L5）。
   - **取整与尾差**：每期金额**向下取整到分**，尾差**全部放末期**；**末期强制 `remaining_after = 0`**——注意这条是**执行末期还款动作时**才置 0，不是排计划时预填（见标注 15），末期本金直接取「还前剩余本金」，不再套公式。依据：银行合同普遍写「末期归还剩余本金 / 最后一期归还剩余本金并支付剩余利息」，尾差并入末期是明确常规；每隔金额是四舍五入还是向下取整各家并不统一，故按你给的兜底取向下取整。
   - **首期不足一整期**：**按整周期计算、首期顺延一个完整周期**。若放款日到首个应还日不是一个完整周期，软件把第一条还款记录**顺延一个完整周期**，首期计息区间取两个相邻应还日之间的完整周期；零头天数不单独成一期、不单独计息。各单位的「一个完整周期」：
     - `month` / `quarter` / `year`：顺延到下下个固定还款日。例 1 月 28 日放款、每月 15 日还款 → 第一条 `2 月 15 日 ~ 3 月 15 日`、应还日 3 月 15 日。
     - `week`：固定**每周周六**，顺延到第二个周六。例周三放款 → 第一条为下下周的周六区间。
     - `day`：**完全能算**——`due_at = start_date + N × 1 天`，第一条就是 `start_date + 1 天`；若按 L3 顺延一个完整周期，则第一条为 `start_date + 2 天`（区间 `+1 天 ~ +2 天`）。
     `end_date` 相应顺延。现实常规是首期按实际天数计息（中行 / 广发 / 公积金合同、江苏银行「首期顺延至第二个还款日」条款），本口径是按你要求做的简化；账单有零头利息时走人工调整（L5）。
   - **计算公式**：
     - `equal_principal` 等额本金：每期本金 = `loan_amount / total_terms` 向下取整到分；每期利息 = 还前剩余本金 × 期利率；末期按上面尾差规则结清。
     - `equal_installment` 等额本息：每期还款额 = `P × r × (1+r)^n / ((1+r)^n − 1)`，P = `loan_amount`、r = 期利率、n = `total_terms`；每期利息 = 还前剩余本金 × r，本金 = 每期还款额 − 利息；末期按剩余本金结清。
     - `interest_first` 先息后本：前 n−1 期只付息 = `loan_amount × r`，末期付息 + 全部本金。
     - `lump_sum` 一次性还清 / `revolving` 随借随还（L4）：**无固定期数、按日单利**，`利息 = 未还本金 × (annual_rate/365) × 实际占用天数`；`lump_sum` 到期一次性算本息，**业务上 `end_date` 必填**（DDL 仍可空、约束在录入层），否则按占用天数计息没有终点；`revolving` 按 `az_liability_loan_draw` 的**支取记录**逐笔分段计息、不提款不计息（见标注 11）。这两类不自动排期，用户主动发起还款时软件算该笔总额。
   - **逾期息费**：过 `due_at` 未还，软件按「罚息（逾期本金为基数）+ 复利（期内未付利息为基数）」算，两者相加写进附表 `penalty_amount`；逾期后不再另计正常期利息，罚息率填合同载明的罚息年利率（常为合同利率上浮 30%~50%），与提前还款违约金默认不同时计。完整公式、依据与合同差异兜底见**贷款附表标注 3 的「逾期计息口径」**。
   - **人工调整**：软件算出的金额**允许人工调整**，改后软件**重算下一条 `pending` 记录**（按全局约定 7，未来永远只有一条，不存在「全部 `pending`」）、次表 `remaining_principal` / `paid_terms`、主表 `total_loss`；被改过的记录 `manual_adjusted = 1`。
   - **用户手填的只有两类**：①动作输入（实还金额、还款时间、还款账户、是否还本期、是否有违约金）；②**本期费用 `fee`**（还款时填，没有就留默认 `'0'`）。金额拆分、剩余本金、下期计划、逾期罚息、提前还款后的重算，**全部由软件写回**（附表标注 8）。主表 `total_loss` 由软件累加，不用手填。
4. 年利率、提前还款违约金率、逾期罚息率都存小数，5% 写 `0.05`。**率在次表、金额在附表**：次表只留 `prepay_penalty_rate` 和 `overdue_penalty_rate`，软件分别算出违约金 / 逾期罚息写入附表 `penalty_amount`，逐笔可查、不会被后一次覆盖；整笔贷款不再单独存一个违约金金额列。软件算出的值**允许人工调整**（L5），改过的记录置 `manual_adjusted = 1` 并重算下一条 `pending`。
5. **期数与单位分开**：`total_terms` / `paid_terms` 只记「多少期」，单位由 `term_unit` 给（默认 `month`，也可 `day` / `week` / `quarter` / `year`），`repay_day` 只在按月类填「每期第几号」。
   **每个单位的 `due_at` 生成规则**——按全局约定 7，**完成一次还款后才生成下一条**，不是一次排完、也不是定时生成；下一条 `due_at` 一律由「上一条 `due_at` + 一个完整周期」算出：
   | `term_unit` | 一条周期多长 | 下一条 `due_at` 怎么算 | `repay_day` |
   |---|---|---|---|
   | `day` | 1 天 | `上一条 due_at + 1 天`；第一条 `start_date + 1 天`（顺延时 +2 天），**完全算得出** | 留空 |
   | `week` | 1 周 | **固定每周周六**，下一条 = 下一个周六；第一条 = 放款后的第一个周六（顺延时第二个周六） | 留空 |
   | `month` | 1 个月 | 下一个月的同一个 `repay_day` 号 | 填「每月几号」 |
   | `quarter` | 3 个月 | `+3 个月`的同号日 | 填 |
   | `year` | 1 年 | `+1 年`的同号日 | 填 |

   `end_date` 按 `start_date + total_terms × 单位` 推（day 加 N 天、week 加 7N 天、month 加 N 月、quarter 加 3N 月、year 加 N 年），别一律当 30 天。**起止时间分两类**：
   - **按期还款类**：主表 `start_date` 必填、`end_date` **界面禁用手动修改，但由上面公式计算得到后存入该列**（选 A，不是不存）；若触发 L3 首期后延，`end_date` 一并顺延一个周期后重算写回。
   - **一次性还清 / 随借随还类**：`total_terms` / `repay_day` 留空，`term_unit` **显式写 NULL**（它默认 `month`，不显式写会带出来），`paid_terms` 保持 0；**没有总期数，主表 `end_date` 由用户自己填且业务上必填**（DDL 仍可空、约束在录入层），不再套上面的公式，也不再允许留空——按占用天数计息必须有终点。
6. **关联账户统一在主表**：这笔贷款整体绑定的账户（放款到账 / 默认扣款）就是主表 `az_liabilities.link_account_id`，**次表不再存**。每一期实际从哪个账户还，由还款附表 `repay_account_id` 记，没单独选就沿用主表那列。账户绑定只主表 + 附表两处，次表这列已删。
7. **抵押必选校验**：`has_collateral` 默认 0；选「是」时 `link_asset_id` **必选**，指向资产主表 `az_assets.id`——房贷车贷就靠它绑回房产车辆。这是录入时的校验，没写进表约束。**同一资产可被多笔贷款指向，每笔一行**：资产侧 `mortgage_state` 只显示「已抵押 / 未抵押」这个二值派生状态，**押了几笔由资产详情页小列表弹窗反查本表得到**（查 `link_asset_id = 该资产` 且 `has_collateral = 1` 的记录），不在资产表存列表、也不存顺位。
   **状态同步时机**：新增本笔且 `has_collateral = 1` 时，把所指向资产的 `mortgage_state` 立即改为「已抵押」；**本笔还清时，为所指向资产重算状态**——查是否还有**其他未结清、未软删**的贷款以该资产为抵押品，有则保持「已抵押」，没有则回「未抵押」。这个动作在负债侧结清流程里一起做，不依赖打开资产页面（详见 A7（房产）标注 5）。登记顺位、登记生效/对抗、拍卖分配、处置结果一概不记。按你指定的放在**贷款次表**，主表不加抵押列。
8. 提前结清由软件收尾：`remaining_principal` 归零 + 主表 `status` 改「已结清」+ **不再生成下一期待还记录**，不是另一种还款方式，不新建行；结清那一笔的应还本息、违约金由软件算好。
9. **贷款侧附表共 3 张**：还款记录表（下表）、支取记录表（标注 11）、以及第六节的分期附表属另一侧。每张都按层级约定同时带 `liability_id`（→ 主表）和 `sub_liability_id`（→ 次表）两列；「分期」次表及其附表见第六节，骨架同款、业务口径另写。
10. **本期费用 `fee` 由用户还款时填写**：次表没有费用率，软件不计算、不预测这笔钱；用户在还款时把本期实际发生的费用（账户管理费、担保费等）填进附表 `fee`，没有就留默认 `'0'`。它照常计入主表 `total_loss`，但不适用 L5 的「软件算出的金额被人工调整」语义——它本来就是用户填的，`manual_adjusted` 不因填 `fee` 而置 1。
11. **随借随还的支取记录表**（用于 L4 分段计息）：`revolving`（随借随还）要按每次支取分段计息，就必须有支取日与金额，故新建 `az_liability_loan_draw`（见下方）。软件按「支取记录 + 还款记录」的时间顺序，对本金余额逐段算 `余额 × 年利率/365 × 占用天数`；`lump_sum`（一次性还清）不用这张表，它在到期日按 `end_date` 一次算本息。
12. **年利率可以由用户修改，软件不做变更重算**：`annual_rate` 允许用户改；改后**只影响之后新生成的期**，已经生成的 `pending` 计划、已经还完的记录一律不重算、不回溯。房贷 LPR 重定价、利率调整这类变化，若用户要让已排好的计划跟着变，走 L5 人工调整，软件不主动做「利率变更 → 批量重算」这种计算。**混合贷（公积金 + 商业贷款）按两笔债务分别录入**：公积金贷款一笔、商业贷款一笔，各有自己的 `annual_rate` 和 `repay_method`，分别计算；不建「组合贷」类型、不在一笔里塞两个利率。
13. **向亲友借入的钱归到「贷款」类**：用 `revolving`（随借随还）、`annual_rate = 0`、无费用、无违约金、无抵押录入；有支取就记一条支取记录，还一次记一条还款记录。不新增第三类债务。
14. **三处口径**：①主表 `status` 与附表 `state` 的状态机（逾期 → 补还 → 生成下期 → 回到正常），见主表标注 4、附表标注 3；②`remaining_after` 在 `pending` 时**留空**、还款后才填，见标注 15；③`end_date`「禁用」＝**界面不让手改、值由计算得到后存入该列**（选 A），见主表标注 5、本标注 5。
15. **`remaining_after` 不预填、一值三用**：软件生成还款记录时**不填** `remaining_after`；只有**执行还款动作、计算出「还款后的剩余本金」**后，才把这个值填入当前这条记录的 `remaining_after`。它同时是三样东西：
    - 次表 `remaining_principal`（这笔债的待还本金）；
    - 当前还款记录的「还后剩余本金」；
    - **下一条还款记录的「还前剩余本金」**——生成下期计划时直接拿它当计算输入，不另存 `remaining_before` 列。
    末期按 L2 强制置 0，也是在执行末期还款动作时做。这样「还完本期 → 生成下期」天然接得上，不需要在 `pending` 记录里预填预测值。两张还款附表同用这套（分期见第六节附表标注 3）。
16. **逾期状态机**：单列在主表标注 4 统一写，贷款 / 分期两张附表共用；贷款附表见下方标注 3。要点是「逾期记录还款前不生成下一条；还款后生成下一条，新记录若已过应还日仍算逾期并继续计罚息；直到生成正常 `pending` 记录，主表 `status` 才回正常」，罚息计入 `total_loss`。

#### 贷款附表：还款记录表 `az_liability_loan_repay`

```sql
CREATE TABLE IF NOT EXISTS az_liability_loan_repay (
  id                 INTEGER PRIMARY KEY AUTOINCREMENT,
  liability_id       INTEGER NOT NULL,  -- → az_liabilities.id（主表主键）
  sub_liability_id   INTEGER NOT NULL,  -- → az_liability_loan.id（次表主键）
  record_source      TEXT    NOT NULL DEFAULT 'auto',  -- 记录来源：auto=软件按计划生成并算好；user=用户主动发起的还款（提前还款 / 一次性类主动还），用户只填动作输入
  term_no            INTEGER,  -- 第几期；一次性还清 / 随借随还留空
  due_at             INTEGER,  -- 应还日
  -- 以下金额列由软件按次表参数计算写入，用户不填（fee 例外：由用户还款时填）
  principal_part     TEXT    NOT NULL DEFAULT '0' CHECK (CAST(principal_part AS REAL) >= 0),  -- 本期本金
  interest_part      TEXT    NOT NULL DEFAULT '0' CHECK (CAST(interest_part AS REAL) >= 0),  -- 本期利息
  remaining_after    TEXT,  -- 还完后剩余本金：生成 pending 时留空，执行还款动作算出后才填

  state              TEXT    NOT NULL DEFAULT 'pending',  -- 状态：未还 / 已还 / 逾期 …
  repaid_at          INTEGER,  -- 实际还款时间，未还留空
  repaid_amount      TEXT,  -- 实还金额，未还留空
  repay_account_id   INTEGER,  -- 还款账户：这一期实际从哪个账户还的，未单独选沿用主表 link_account_id
  manual_adjusted    INTEGER NOT NULL DEFAULT 0,  -- 人工调整标记：软件算出的金额被人工改过=1，未改=0；允许值：0/1（0=未改，1=已人工调整）
  note               TEXT    NOT NULL DEFAULT '',  -- 说明；penalty_amount 的各项构成由软件自动追加在此（用户不用手填）
  created_at         INTEGER NOT NULL,
  updated_at         INTEGER NOT NULL,  -- 更新时间
  revision           INTEGER NOT NULL DEFAULT 1  -- 版本号
);

CREATE INDEX IF NOT EXISTS idx_az_liability_loan_repay
  ON az_liability_loan_repay (liability_id, term_no);

CREATE INDEX IF NOT EXISTS idx_az_liability_loan_repay_due
  ON az_liability_loan_repay (state, due_at);
```

**标注**

1. **一期一条，计划由软件生成并算好**：等额本金 / 等额本息每期一条；先息后本每期一条、到期那条带全部本金；一次性还清 / 随借随还没有期数，`term_no` 留空，通常就一条。
   **按期还款类**（次表标注 2/3）：用户填好贷款数据后，软件按公式算出第 1 期各金额并写入 `pending` 记录；用户还掉当期（确认「已还」）后，软件再算好并生成**下一条待还（`pending`）**，直到最后一期。**用户不自己生成计划记录、不填金额**。生成时 **`remaining_after` 留空**，只有执行还款动作后才填（次表标注 15）。**一次性还清类不自动排期**，用户主动发起还款时由软件算该笔总额。
   **用户手动新增的还款记录只用于「主动提前还款」**：走标注 8 的「是否有违约金」+「是否还本期」两个开关，用户只填动作输入，拆分与重算由软件完成。两类记录用 `record_source` 区分（标注 9）。
2. **本表金额由软件计算写入，不由用户抄账单**：本期本金 / 利息，都按次表的本金 / 利率 / 期数 / 还款方式由软件算出（公式见次表标注 3）；违约金由软件按「提前还本金额 × `prepay_penalty_rate`」算出；逾期息费按下方标注 3「逾期计息口径」算（罚息 + 复利、率取合同罚息年利率）；这些额外费用**相加**写入 `penalty_amount`，并由软件把构成追加进 `note`（标注 3 / 次表标注 3）。**两个生成时不填的例外**：`fee`（本期费用）由用户还款时填写（次表标注 10），软件不算、不预测；`remaining_after`（还完后剩余本金）生成 `pending` 时留空，**执行还款动作算出后才填**（次表标注 15）。用户手填的只有**动作输入**（实还金额、还款时间、还款账户、是否还本期、是否有违约金）+ **本期 `fee`**。**软件算出的金额允许人工调整（L5）**，人工改过的记录置 `manual_adjusted = 1`，并由软件重算下一条 `pending`、次表进度与主表 `total_loss`（标注 9）；用户自填的 `fee` 不触发 `manual_adjusted`。
3. **逾期状态机（与分期附表标注 8 同款，主表标注 4 是总纲）**：`state` 默认「未还」（`pending`），还清改「已还」；枚举不写 CHECK，取值由业务层管。`repaid_at` / `repaid_amount` 未还时留空，还了才填。完整流转：
   - 过 `due_at` 仍未还 → 该记录 `state` 改「**逾期**」，软件按下方「逾期计息口径」算出罚息 + 复利写入本表 `penalty_amount`，**计入主表 `total_loss`**（用户在整笔债务里操作导致的实际支出），构成由软件追加进 `note`；**主表 `status` 同步改「逾期」**；
   - **这条逾期记录还款之前，不生成下一条还款记录**；
   - 还款后 → 生成下一条并做计算（按标注 4 的新剩余本金）；**若新记录的 `due_at` 已过**（生成时当前时间晚于应还日）→ 它同样直接标「逾期」、按时间算罚息，主表保持「逾期」，继续不生成再下一条；
   - **直到某次生成的下一条记录是正常「未还（`pending`）」状态，主表 `status` 才标回「正常」**。

   **逾期计息口径**——上面状态机里「算罚息」的具体算法按现实常规补齐：
   - **逾期后不再另计正常期利息**：当期已经算好的 `interest_part` 不重算、不逐日累加；自逾期之日起改按**罚息利率**对逾期本金计收罚息，直至清偿本息为止。依据：中国人民银行《关于人民币贷款利率有关问题的通知》（银发〔2003〕251 号）第三条「从逾期之日起，按罚息利率计收利息，直至清偿本息为止」；工行融 e 借、上海银行、中信个人借款协议均写「对所欠本金按执行利率加收 50% 按日计收罚息」。
   - **计息基数取「逾期未还本金」**，不是「应还未还额」。依据：甘肃法院网「逾期利息以逾期借款本金为基数」、2026 年《个人贷款业务明示综合融资成本自律规范》示例「逾期利率以逾期本金为基数计收」、工行/上海银行/中信合同。个别合同（如中行个人贷款合同）把「应付未付利息」也并进基数算 `(本金+应付未付利息) × 日罚息利率`，**属合同差异，走 L5 人工调整**，软件不默认按这种算。
   - **复利**：对到期应付未付的**期内利息**，按罚息利率计收复利；复利基数只取期内未付利息，**不含罚息本身**（不对罚息再计复利）。依据：251 号文第三条「对不能按时支付的利息，按罚息利率计收复利」；揭阳中院典型案例「若合同无特殊约定，复利一般以借款期限内的应付未付利息为基数，逾期罚息不能作为复利基数」。
   - **公式**：`罚息 = 逾期未还本金 × (overdue_penalty_rate/365) × 逾期天数`，`复利 = 未付期内利息 × (overdue_penalty_rate/365) × 逾期天数`，两者相加写本表 `penalty_amount`，计入 `total_loss`。日基准按 `/365`；合同按 `/360`（如中行日罚息利率）的差异走人工调整。
   - **罚息率填什么**：`overdue_penalty_rate` 填**合同载明的逾期罚息年利率**（常为合同利率上浮 30%~50%，如合同利率 6% → 罚息 9%，写 `0.09`），不是 `annual_rate` 那个正常年利率；5% 上浮 50% 之类的换算由用户按合同录入。
   - **与提前还款违约金不叠加**：两者是不同事件——现实里提前还款前须先清偿全部到期未付款项（工行融 e 借 7.2），且司法上逾期罚息与违约金一般**二选一**、不支持同时适用（广东高院《审理金融机构借贷纠纷案件的指导意见》第 26 条）。所以同一条记录里默认只出现一种；真遇到平台两边都收，按账单人工调整 `penalty_amount`，**由软件在 `note` 自动追加构成说明**，**不为此拆新列**。
   - **`penalty_amount` 是「总费用合计」**：这一列装的是**本条记录所有额外费用 / 罚费的合计**——提前还款违约金、逾期罚息、复利，有哪几项就相加哪几项，**不拆列、不加用途标记**。软件在处理还款动作时本来就知道用户发生了哪种行为（提前还 / 逾期 / 结清），因此由**软件自动**把「各项名称 + 各自金额 + 合计」追加进本条 `note`，例如 `提前还款违约金 40.67；逾期罚息 6.96；复利 1.20；合计 48.83`。用户不用手填、事后可追溯，不需要新增字段。
   - **清偿顺序**：不另定「费用 → 利息 → 本金 → 违约金」这类扣划顺序，直接由主表标注 4 的**递归式**确定——`余额 = 本次还款额 − 本次还款记录额 − 逾期费用`，先清当前这条的本息 + 逾期费用，余额再用于下一条，依次类推。现实合同里的多种扣划顺序（江苏银行个人消费贷款额度合同、中信个人借款协议 3.7）与本项目简化口径不一致时，按 L5 人工调整；本条不再是待定项。
4. 每**还完一期**（当期改「已还」），软件先算出「还款后的剩余本金」，填入本条 `remaining_after`，并同步把次表 `paid_terms` +1、`remaining_principal` 改成同一个值；**这个值同时是下一条还款记录的「还前剩余本金」**，生成下期计划时直接拿来算，不另存列（次表标注 15）。附表金额与次表进度由软件一次算好写回，不存在「两处对不上要人工修」。手动还款选「否」只是直接冲本金、不算还完一期，`paid_terms` **不加**，软件只改 `remaining_principal` 并重算当期待还（标注 8）。**生成 `pending` 时 `remaining_after` 留空**，不是填预测值。
5. **总亏损口径**：主表 `total_loss` = 所有亏损之和 = 已还各期 `interest_part + fee + penalty_amount` 合计 **+ 次表 `service_fee`（放款时先扣的服务费）**。其中 `fee` 是用户还款时填的本期费用（次表标注 10），`interest_part` / `penalty_amount` 由软件算；**逾期罚息也写在 `penalty_amount` 里、照常计入 `total_loss`**（标注 3）——它是用户在整笔债务中操作导致的实际支出，不是账面数字。违约金**逐笔**记在本表 `penalty_amount`、不再单列在次表，也不混进本表 `fee`，别加两遍；`service_fee` 是次表独立一列、本表没有，同样别重复加。主表那列只存结果、不存明细，由软件按上述公式累加写入，不用用户填。
6. 留痕三件套 `created_at` / `updated_at` / `revision` 齐全。
7. **还款账户**：`repay_account_id` 记这一期实际从哪个账户扣的钱，可逐期不同；没手动选就沿用**主表** `link_account_id`（这笔贷款绑定的账户）。未还的那期先留空，还了再填。放款到账账户与每期扣款账户因此能分开记，不用挤在一列。
8. **用户主动发起的提前还款**（`record_source = 'user'`，本表唯一由用户新建的记录类型）：用户只填**动作输入**——实还金额、还款时间、还款账户、「是否还本期」、「是否有违约金」；**其余全部由软件计算并写回**。

   **「是否有违约金」是用户唯一保留的决定**：
   - 选「**否**」→ 软件置 `penalty_amount = 0`。
   - 选「**是**」→ 软件按 **`penalty_amount = 提前还本金额 × prepay_penalty_rate`** 算。**计算基数默认取「提前还本金额」**，即本次还款里拿来提前偿还本金的钱：选「还本期」时是下面的 `余额 = 实还金额 − 当期总还`，选「不还本期」时是整笔实还金额（全部直接冲本金）。这里取的是**扣违约金前**的数，这样 `penalty` 和 `剩余还本 = 余额 − penalty` 不会互相依赖。软件算出的是默认值，**合同有特殊约定时允许人工调整**（L5）：改后本条 `manual_adjusted = 1`，软件按改后的值重算下一条 `pending` 及主表 `total_loss`。
   - 软件仍**不判断「本次是不是一次性还清、该不该收违约金」**：一次性还清若确实要收，用户自己勾「有违约金」，软件按率算金额；不收就不勾。

   **「是否还本期」决定软件往哪写**：
   - **选「是」**：软件算 **当期总还** = `principal_part + interest_part + fee`（本金 + 利息 + 费用）。**当期那条 `auto` 计划记录改「已取消」**，由本条 `user` 记录承载该期本息与实还、状态「已还」——同一期不会留两条 `paid`，`total_loss` 才不会把当期利息算两遍。再按公式拆实还金额：

     ```
     余额           = 实还金额 − 当期总还
     剩余还本金额   = 余额 − 本条 penalty_amount
     ```

     「剩余还本金额」全部冲减 `remaining_principal`；软件按新的剩余本金**算好并生成下一条待还（`pending`）**记录（标注 1）。`paid_terms` 只 +1 一次，多还的本金不额外加期。
   - **选「否」**：不结清当期，实还金额直接冲本金，软件改 `remaining_principal` 并按新本金**重新计算当期待还记录**的本金 / 利息 / `remaining_after`；当期仍 `pending`、不生成下期、`paid_terms` 不加。

   **软件自动判断结清**：两种分支下只要 `remaining_principal` 归零，一律不再生成下期、当期收尾、主表 `status` 改「已结清」（次表标注 8）。**提前还款后对应的所有数据计算（拆分、剩余本金、下期计划、当期重算、状态、次表进度、主表 `total_loss`）全部由软件完成**，用户不再手填任何结果。违约金记本表 `penalty_amount`，不记进 `fee`（标注 5）。
9. **两类记录靠 `record_source` 区分**：`auto` = 软件按计划生成并算好金额的待还记录（按期类的逐期计划），用户只确认「已还」、不改金额；`user` = 用户主动发起的还款（提前还款，以及一次性还清 / 随借随还类主动还的那笔），用户只填动作输入，金额拆分与后续重算由软件完成。**常规按期还款不再由用户新建记录**。**同一期只留一条 `paid`**：用户对该期提前还款时，原 `auto` 计划改「已取消」、由 `user` 记录承载该期本息，避免 `total_loss` 双计。取值不写 CHECK，由业务层管。`manual_adjusted = 1` 只表示该条金额被人工改过，不改变记录来源；软件从该条起重算下一条 `pending`（L5）。

#### 贷款附表：支取记录表 `az_liability_loan_draw`

```sql
CREATE TABLE IF NOT EXISTS az_liability_loan_draw (
  id                 INTEGER PRIMARY KEY AUTOINCREMENT,
  liability_id       INTEGER NOT NULL,  -- → az_liabilities.id（主表主键）
  sub_liability_id   INTEGER NOT NULL,  -- → az_liability_loan.id（次表主键）
  draw_amount        TEXT    NOT NULL CHECK (CAST(draw_amount AS REAL) > 0),  -- 本次支取金额
  drawn_at           INTEGER NOT NULL,  -- 支取日
  note               TEXT    NOT NULL DEFAULT '',  -- 说明
  created_at         INTEGER NOT NULL,
  updated_at         INTEGER NOT NULL,
  revision           INTEGER NOT NULL DEFAULT 1
);

CREATE INDEX IF NOT EXISTS idx_az_liability_loan_draw
  ON az_liability_loan_draw (sub_liability_id, drawn_at);
```

**标注**

1. **只给 `revolving`（随借随还）用**：`lump_sum`（一次性还清）不写这张表，它在到期日按 `end_date` 一次算本息；其余三种按期还款方式也没有支取动作。
2. **补的是 L4 的缺口**：L4 要求「按每次支取 / 还款分段计息、不提款不计息」，软件按「支取记录 + 还款记录」的时间顺序，对每一段本金余额算 `余额 × (annual_rate/365) × 占用天数`，各段利息相加即该笔应还利息。
3. **余额联动**：支取时 `remaining_principal += 本次支取金额`，还款时按还款记录冲减；累计支取不超过 `loan_amount`（循环额度）。向亲友借入的钱（标注 13）也走这张表记「借到多少」。
4. 按层级约定带 `liability_id` + `sub_liability_id` 双引用，留痕三件套齐全，金额列为 `TEXT` 十进制字符串。

**贷款口径提醒**

1. **还款方式分类不另建列**：「按期还款类 / 一次性还清类」直接看 `repay_method` 五个枚举值判定。
2. 主表 `start_date` / `end_date` 的 DDL **仍是可空**（保持录入层校验），没改成 NOT NULL 或加约束。
3. **L4 计息口径**：`lump_sum`（一次性还清）/ `revolving`（随借随还）**按日单利计息**，`利息 = 未还本金 × (annual_rate/365) × 实际占用天数`；`lump_sum` 到期一次性算本息、`end_date` 业务必填，`revolving` 按 `az_liability_loan_draw` 支取记录逐笔分段计息、不提款不计息。合同另有计息方式（按 360 天、复利、最低计息天数等）的，按 L5 人工调整账单金额并置 `manual_adjusted = 1`。其余计算细节（期利率、取整尾差、首期后延）见标注 3。

## 六、负债侧：分期次表 `az_liability_installment`

> 参考第五节贷款次表做了减法：分期没有放款、没有抵押、恒按月、固定期数。**两个账户字段含义不同**，见标注 2。

```sql
CREATE TABLE IF NOT EXISTS az_liability_installment (
  id                    INTEGER PRIMARY KEY AUTOINCREMENT,
  liability_id          INTEGER NOT NULL UNIQUE,  -- → az_liabilities.id（主表主键）
  installment_amount    TEXT   NOT NULL CHECK (CAST(installment_amount AS REAL) > 0),  -- 分期总额（订单 / 账单金额）
  remaining_principal   TEXT   NOT NULL CHECK (CAST(remaining_principal AS REAL) >= 0),  -- 剩余待还本金
  total_terms           INTEGER NOT NULL,  -- 总期数，固定 N 期、恒按月
  paid_terms            INTEGER NOT NULL DEFAULT 0,  -- 已还期数
  repay_day             INTEGER,  -- 还款日：每期第几号
  annual_rate           REAL   CHECK (annual_rate IS NULL OR annual_rate >= 0),  -- 年利率，5% 写 0.05；有息计费填，免息计费留空/0。软件按它算利息写附表 interest_part
  per_term_fee_rate     REAL   CHECK (per_term_fee_rate IS NULL OR per_term_fee_rate >= 0),  -- 每期手续费率，5% 写 0.05；软件按它算手续费写附表 fee（与年利率分开两笔）
  overdue_penalty_rate  REAL   NOT NULL DEFAULT 0 CHECK (overdue_penalty_rate >= 0),  -- 逾期罚息率（年化，合同载明的罚息利率，常为合同利率上浮 30%~50%，不是正常年利率），9% 写 0.09；软件按「逾期本金 × 率/365 × 逾期天数」算罚息，并对到期应付未付的期内利息按同率计复利
  mount_creditcard_id   INTEGER,  -- 挂载信用卡 → 账户侧信用卡账户；仅信用卡分期填，商品分期留空（关联标记）
  created_at            INTEGER NOT NULL,
  updated_at            INTEGER NOT NULL,
  revision              INTEGER NOT NULL DEFAULT 1
);
```

**标注**

1. 一笔分期一行，`liability_id` 唯一指向主表。`installment_amount` 是订单 / 账单总额，`remaining_principal` 是现在还欠多少，还一次改一次。分期是「把一笔已发生的消费拆成 N 期」，**没有放款**，所以贷款次表 `loan_amount` / `actual_received_amount` / `service_fee` 那套金额关系三列全砍，只留总额 + 剩余本金。
2. **两个账户别混**：
   - 主表 `link_account_id` = 用户**用哪张卡 / 账户来还**这笔分期（还款账户），所有分期都可能有，跟贷款同一列、同一语义。
   - 次表 `mount_creditcard_id` = **挂载信用卡**，是「信用卡分期 / 账单分期」的关联标记，指向账户侧那张信用卡；**商品分期、电商分期、租金分期不挂卡，留空**。
   - 一个是「钱从哪还」，一个是「这笔分期从哪张卡的账单分出来的」，方向不同、可同时存在，甚至可能不是同一张卡。附表 `repay_account_id` 沿用主表那列，别错用到 `mount_creditcard_id`。
3. **分期类型不单列**：是不是信用卡分期，看 `mount_creditcard_id` 填没填就知道；买了什么、哪笔订单用主表 `name` / `note`。跟前面「分类不另建列」一个路子。
4. **期数恒按月、起止时间**：`total_terms` 是签约时的 N 期、`paid_terms` 已还期数，**不单列 `term_unit`**（贷款那列是给月 / 季 / 年准备的，分期用不上）。主表 `start_date` 必填；`end_date` 由 `start_date + total_terms × 月` **计算得到后存入该列、界面禁用手动修改**（算出存入、界面禁用手改，与贷款同款）；没有贷款那种「一次性类可编辑到期日」的例外。I6 模式 A「缩短期数」会减 `total_terms`，软件按新的 `total_terms` 重算并写回 `end_date`。
5. **还款计算由软件完成**：
   - **利率与费率分开、两个金额列各归各**：分期确实有「利率」这回事，次表新增 `annual_rate`（年利率，5% 写 `0.05`）。**利率算出来的钱归 `interest_part`（利息），费率算出来的钱归 `fee`（手续费）**，两列天然分开，不需要再建「计费类型」列：
     - **免息计费** = 没有利息、只有手续费：`annual_rate` 留空 / 0 → `interest_part = 0`；每期手续费 = `installment_amount × per_term_fee_rate` → 记 `fee`。
     - **有息计费** = 既有利息又有手续费：`annual_rate > 0` → 每期利息 = 还前剩余本金 × (`annual_rate / 12`)（分期恒按月，折算同贷款）→ 记 `interest_part`；每期手续费仍 = `installment_amount × per_term_fee_rate` → 记 `fee`。两笔并存、各记各列。
     - 判定只看 `annual_rate` 有没有值（空 / 0 即免息），软件据此决定 `interest_part` 是否为 0。
   - **计费方式：按期收**。不做首期一次性收齐、不做按剩余本金计息。每期应还 = 每期本金 + 每期利息 + 每期手续费。
   - **计划生成：统一成逐期生成**，跟贷款一致。用户填好分期数据后，软件只算好**第 1 期**金额并写入一条 `pending`；还完当期后软件再算好并生成**下一条 `pending`**，直到 `total_terms` 跑完。不再「签约一次排 N 条」。用户不自己生成、不填金额。
   - **每期本金** = `installment_amount / total_terms`，**向下取整到分、尾差全部放末期、末期强制 `remaining_after = 0`**（与贷款取整规则同一套）；**`remaining_after` 生成 `pending` 时留空，执行还款动作算出后才填**（见附表标注 3）。
   - **逾期罚息**：过 `due_at` 未还，按「罚息（逾期本金为基数）+ 复利（期内未付利息为基数）」算、逾期后不再另计正常期利息，相加写入附表 `penalty_amount` 并计入 `total_loss`；公式、罚息率填写口径与依据**与贷款附表标注 3「逾期计息口径」完全共用**（状态机见附表标注 8）。
   - **人工覆盖**：软件算出的金额允许人工覆盖，被改过的记录 `manual_adjusted = 1`，软件重算下一条 `pending` 与 `total_loss`。
   - 监管要求息费展示统一采用利息形式、不得只给「一次性收取全额利息」的默认项，所以账单上叫利息还是手续费由平台定，附表按计费方式分列写。
6. **没有抵押**：`has_collateral` / `link_asset_id` 全砍，分期不可能有抵押物。
7. **总负债合计**：信用卡分期（`mount_creditcard_id` 非空）**不进合计**——卡上欠款与分期剩余本金是同一笔钱，两处都加就翻倍；**不挂卡的商品 / 租金分期单独进合计**——没有账户汇总兜底，是用户实际支出、只是滞后了。**花呗 / 白条归信用卡账户后按挂卡分期处理，不进合计**（主表标注 7），别再把「电商分期」笼统算进这一项。公式见主表标注 2。
8. **能否提前还：能，且是用户主动申请**（客服 / APP 结清页），账本不自动触发。现实里两种都有：
   - **全额提前结清**：主流，花呗就只支持整笔结清、不支持指定还某几个月。
   - **部分提前还**：农行、工行等支持，中行部分产品（现金分期随借随还）亦可，且会改剩余计划——期数自动减少，或期数不变但每期本金 / 利息减少，规则各家不同。
   提前还款由用户主动发起，但**结清应还多少、剩余计划怎么改，全部由软件算好并写回**（见附表标注 7），用户只填实还金额等动作输入；软件不自动触发提前结清。
9. **需不需要手续费：需要，而且没有统一算法**，这是不照抄贷款的根本原因：
   - 已收手续费**一律不退**，各家一致。
   - 剩余手续费：有的**一次性收齐剩余各期**（建行 / 招行 / 浦发），有的**只加收一期未出账单手续费**（农行 2019 年后），有的**免收未出账利息、只收当期**（工行 / 中行），有的改按**剩余未下账本金 3% 收违约金**（兴业），有的**免未产生手续费但另收一笔「提前还清手续费」**（花呗），有的收「提前结清服务费」（白条）。
   - 监管口径：客户提前结清信用卡分期的，按**实际占用资金金额及期限**计收利息，并按法律法规和合同约定计收费用（中国银保监会、中国人民银行《关于进一步促进信用卡业务规范健康发展的通知》2022 第二十二条）。
   所以**软件按一个明确规则算提前结清金额，而不是让用户抄结清页**：按「剩余未还本金 + 按规则算出的剩余手续费 / 提前结清服务费 / 违约金」算好并写入附表，用户不填结果。**规则怎么定：每笔结清时由用户选**，因为分期录入时往往不知道平台会按哪种收，只有提前还款时才分得出来；不做成次表字段、也不永远按默认。所选规则存该笔 `user` 结清记录的 `settle_rule`，软件据此计算。可选值：免收未出账 / 收齐剩余各期 / 只加收一期 / 按剩余本金比例 / 另收一笔提前结清服务费。
   **规则输入列**：附表有 `settle_rule_ratio`（选「按剩余本金比例」时用户填的比例，5% 写 `0.05`）和 `settle_service_fee`（选「另收一笔提前结清服务费」时用户填的金额），各只服务于对应规则、其余规则留空；这样事后能追溯当时按多少算的。
   **为什么分期要用户选「是否提前结清」、贷款不用**：贷款侧软件能直接按 `prepay_penalty_rate` 算违约金、按本息算应收，结清金额是唯一确定的，所以还款时**不需要用户提醒「是否一次性还清」**，软件只判断是否全部还完；分期结清规则各家不同、软件无法预知，所以**分期还款时用户必须先选「是否提前结清」**，选「是」→ 再选 `settle_rule` → 填规则所需输入（`settle_rule_ratio` / `settle_service_fee`）→ **软件按规则算出「结清应还总额」，与用户填的实还金额比对验证是否准确**，不一致就提示核对，确认后以规则算出的金额为准写回；选「否」→ 走部分提前还（两种模式）。「是否提前结清」是录入/还款时的动作开关，不写进表；`record_source = 'user'` 已能区分这类主动发起的记录。展开见附表标注 7。
10. **与贷款同一套计算机制、不同公式**：分期的常规计划（次表标注 5）和提前还款（附表标注 7）**都由软件计算并写回**，跟贷款一致。差别只在输入与公式——分期次表没有 `prepay_penalty_rate`，`per_term_fee_rate` 是每期手续费率、`annual_rate` 是年利率，都不是结清费率，所以提前结清那笔按「该笔所选的剩余手续费规则 + 规则输入列」算（标注 9、附表 `settle_rule` / `settle_rule_ratio` / `settle_service_fee`），**不套**贷款的「提前还本金额 × 违约金率」；且分期要用户先选「是否提前结清」、软件按规则**验证实还金额是否准确**（标注 9），贷款则不需要这个提醒、软件直接算。用户只填动作输入，软件自动判断「是否全部还完」并写回全部结果。
11. **监管边界**：不得对已办理分期的资金余额**再次办理分期**、不得对分期业务提供**最低还款额服务**、分期期限不得超过 **5 年**（同通知第十九、二十条）。前两条是附表标注 4「新建独立分期」的上游依据；「不超过 5 年」是录入时 `total_terms ≤ 60` 的上限参考，没写进表约束。
12. 分期还款记录附表见下方，已按层级约定同时带 `liability_id`（→ 主表）和 `sub_liability_id`（→ 次表）两列。

#### 分期附表：还款记录表 `az_liability_installment_repay`

```sql
CREATE TABLE IF NOT EXISTS az_liability_installment_repay (
  id                 INTEGER PRIMARY KEY AUTOINCREMENT,
  liability_id       INTEGER NOT NULL,  -- → az_liabilities.id（主表主键）

  term_no            INTEGER NOT NULL,  -- 第几期：这条还款记录对应分期合同的第几期，1..total_terms；全额提前结清的 user 记录填「当期期号 = paid_terms + 1」，见标注 7
  due_at             INTEGER,  -- 应还日
  -- 以下金额列全部由软件按次表参数计算写入，用户不填（允许人工覆盖，见 manual_adjusted）
  principal_part     TEXT    NOT NULL DEFAULT '0' CHECK (CAST(principal_part AS REAL) >= 0),  -- 本期本金
```

**标注**

1. **统一成逐期生成（与贷款同款）**：用户填好分期数据后，软件只算好**第 1 期**的本金 / 利息 / 手续费，写入一条 `pending` 记录；用户还掉当期（确认「已还」）后，软件再算好并生成**下一条 `pending`**，直到 `total_terms` 跑完。**用户不自己生成、不填金额**，不再「签约一次排 N 条」。生成时 **`remaining_after` 留空**，执行还款动作后才填（标注 3）。`state` 默认 `pending`，过了 `due_at` 仍未还改「逾期」并算罚息（标注 8），提前结清时当期那条 `auto` 计划改「已取消」；枚举不写 CHECK，取值由业务层管。
   **用户手动新增的还款记录只用于「主动提前还款」**（`record_source = 'user'`），走标注 7；两类记录见标注 9。
2. **本表金额由软件计算写入，不由用户抄账单**：本金按总额 / 期数，**利息只由次表 `annual_rate` 算出记 `interest_part`，手续费只由次表 `per_term_fee_rate` 算出记 `fee`**——两列各归各，免息计费（年利率空 / 0）时 `interest_part = 0`、手续费照记 `fee`，有息计费时两列都有值（公式见次表标注 5）。**提前结清那一笔的剩余手续费 / 违约金 / 服务费由软件按该笔 `settle_rule` 及输入列算，逾期罚息由软件按 `overdue_penalty_rate` 算**。用户手填的只有**动作输入**：实还金额、还款时间、还款账户、**是否提前结清**、结清规则 + 规则输入值、部分提前还的重算模式；`repaid_at` / `repaid_amount` 未还留空，还了才填。**生成 `pending` 时 `remaining_after` 留空**（标注 3）。**软件算出的金额允许人工覆盖（I7）**，改过的记录置 `manual_adjusted = 1`，软件重算下一条 `pending` 与 `total_loss`（标注 9）。附表仍是逐期留痕，只是值的来源从「用户抄」变成「软件算」。
3. **`remaining_after` 不预填、一值三用（与贷款附表标注 4 同款）**：生成 `pending` 记录时 `remaining_after` **留空**；只有**执行还款动作、算出「还款后的剩余本金」**后才填入本条。这个值同时是：次表 `remaining_principal`、当前记录的「还后剩余本金」、**下一条还款记录的「还前剩余本金」**（生成下期计划直接拿它当计算输入，不另存列）。每还完一期，软件同步把次表 `paid_terms` +1；`paid_terms` 只记**实际还完的期数**，提前结清不硬补到 `total_terms`。全部还完则软件把主表 `status` 改「已结清」。末期按 L2 强制 `remaining_after = 0`，也是在执行末期还款动作时做。
4. **第二个月又走分期 = 新建一行独立分期**（连带它自己的逐期还款记录），原行一期都不动。监管明确「不得对已办理分期的资金余额再次办理分期」；「当期的分期就看当期花了多少」，各笔各跑各的，互不减、互不并——这正是前面怕的「利息计重」在表结构上的解法（次表标注 11）。
5. **息费分工与 `total_loss` 口径**：提前结清相关金额由软件按所选规则算好写进这两列，**同一次收费只进一列、别重复计**：
   - `fee` = 本期手续费 / 软件算出的提前结清**剩余手续费**；
   - `penalty_amount` = 软件算出的提前结清**违约金 / 提前结清服务费**（按剩余本金比例或固定一笔那种）。
   两者都**由软件算、不由用户填**，只是不套贷款的「提前还本金额 × 违约金率」，理由见次表标注 9 / 10。**分期 `total_loss` 口径定死** = 已还各条 `interest_part + fee + penalty_amount` 合计，**没有 `service_fee` 项**（分期无放款，不产生放款服务费）；**逾期罚息也写在 `penalty_amount`、照常计入 `total_loss`**（标注 8）——是用户在整笔债务中操作导致的实际支出。主表那列由软件累加写入。跟贷款「所有亏损之和」同一把尺子，只是少了放款那一笔。
   **`penalty_amount` 是总费用合计**：本条所有额外费用 / 罚费（提前结清违约金、服务费、逾期罚息、复利）相加即这一列，**不拆列、不加用途标记**；软件知道每笔是什么行为，把「各项名称 + 金额 + 合计」**自动追加进本条 `note`**，用户不用手填，口径与贷款附表标注 3 完全一致。
6. **还款账户**：`repay_account_id` 沿用主表 `link_account_id`（用哪张卡还），没单独选就沿用它；别和次表 `mount_creditcard_id`（挂载信用卡）搞混。
7. **用户主动发起的提前还款怎么落（`record_source = 'user'`，配合贷款附表标注 8）**：用户只填动作输入——实还金额、还款时间、还款账户、**是否提前结清**、**结清规则 `settle_rule`（I5）+ 规则输入值**、**部分提前还的重算模式（I6）**；**结清应还多少、下一条计划怎么算，全部由软件写回**。
   **第一道开关是「是否提前结清」**：分期结清规则各家不同、软件无法预知，所以还款时用户必须先选；选「是」走下面的全额结清，选「否」走部分提前还（I6）。贷款侧没有这个开关——贷款软件能直接按本息和 `prepay_penalty_rate` 算出唯一确定的结清金额，只判断「是否全部还完」即可（次表标注 9）。

   - **全额提前结清（I5）**：`settle_rule` 由用户在该笔结清时选（免收未出账 / 收齐剩余各期 / 只加收一期 / 按剩余本金比例 / 另收一笔服务费），因为分期录入时往往不知道平台按哪种收。**规则所需输入一并落库**：选「按剩余本金比例」填 `settle_rule_ratio`（5% 写 `0.05`），选「另收一笔服务费」填 `settle_service_fee`（金额），其余规则两列留空。**软件按所选规则和输入算出「结清应还总额」，与用户填的 `repaid_amount` 比对验证是否准确**——不一致就提示用户核对，确认后以规则算出的金额为准写回；确属平台特殊口径的走 `manual_adjusted` 人工覆盖。软件把剩余手续费 / 服务费 / 违约金写入本条 `user` 记录、改「已还」，`remaining_principal` 归零；**当期那条 `auto` 计划改「已取消」**（逐期生成下只有当期一条未来计划，没有「剩余 N 条」要作废）——不删行、留痕，不补 `paid_terms`，同一期不留两条 `paid` 以免 `total_loss` 双计；主表 `status` 改「已结清」、不再生成下期。
     **`term_no` 是什么、结清时填什么**：`term_no` 就是「**这条还款记录对应第几期**」，取值 `1..total_terms`。全额提前结清的 `user` 记录**填当期期号 = `paid_terms + 1`**（即它承接的正是当期那笔）；由于当期 `auto` 计划已改「已取消」，这一期仍然只有一条 `paid`，不存在同号冲突，也不必把 DDL 改成可空。首期未还就结清时，`paid_terms = 0`，填 1。
   - **部分提前还（I6）**：软件落一条还款记录、冲减 `remaining_principal`，**重算模式由用户选两种**：
     - **模式 A「缩短期数、每期金额不变」**：用户还款额可能不会刚好覆盖某一期，因此**选本模式时校验实还金额必须 = k × 每期应还额（k 为正整数）**，不满足则不允许选 A（提示改金额或改选 B）。满足时软件把 k 期提前还掉：`total_terms` 减 k、`paid_terms` 不变，后续每期金额不变，按新剩余本金继续逐期生成下一条 `pending`。**手续费提示**：该模式按整期额收，未出账手续费是否退由平台规则决定，校验时提示用户核对；与账单不符的走 `manual_adjusted` 人工调整，软件把差异构成写进 `note`，不改变整期额校验本身。
     - **模式 B「期数不变、每期金额变少」**：`total_terms` 不变，软件按 `新剩余本金 / (total_terms − paid_terms)` 重算每期本金、手续费按 `per_term_fee_rate` 算，生成下一条 `pending`。
     - 两种模式下 `paid_terms` 都只记**实际还完的期数**，提前还掉的部分不硬补。
   - **软件自动判断结清**：只要 `remaining_principal` 归零，一律不再生成下期、当期收尾、主表 `status` 改「已结清」；同时把次表进度、下一条 `pending` 金额、主表 `total_loss` 一次算好写回。用户不再手填任何结果。
8. **逾期状态机（与贷款附表标注 3 同款，主表标注 4 是总纲）**：过 `due_at` 未还 → 该记录 `state` 改「**逾期**」，软件按下方口径算出罚息 + 复利写入本表 `penalty_amount`，**计入主表 `total_loss`**（用户在整笔债务里操作导致的实际支出），**主表 `status` 同步改「逾期」**；**这条逾期记录还款之前不生成下一条还款记录**；还款后生成下一条并做计算，**若新记录 `due_at` 已过则它也直接标「逾期」、继续计罚息**，主表保持「逾期」；**直到生成的下一条记录是正常「未还（`pending`）」状态，主表 `status` 才标回「正常」**。
   **逾期计息口径（与贷款附表标注 3 完全共用）**：逾期后**不再另计正常期利息**；罚息以**逾期未还本金**为基数，按 `逾期本金 × (overdue_penalty_rate/365) × 逾期天数` 算；对到期应付未付的期内利息按同率计**复利**（复利基数不含罚息本身）；两者相加写 `penalty_amount`。`overdue_penalty_rate` 填合同载明的罚息年利率（常为合同利率上浮 30%~50%），日基准沿用 L1 的 `/365`，按 `/360` 的合同差异走人工调整。依据与不叠加规则（罚息 vs 提前结清违约金 / 服务费二选一、真同时收则人工调整 + 软件在 `note` 写构成、不拆列）见贷款附表标注 3；**允许人工覆盖**，改过置 `manual_adjusted = 1`。
   **一次补足多期＝递归处理**：与贷款侧完全同款，按主表标注 4 的递归式 `余额 = 本次还款额 − 本次还款记录额 − 逾期费用`，余额继续还下一条、生成下一条，依次类推；清偿顺序、罚息截止时点都由这条递归确定，不再另定扣划顺序。**运行依据**：软件不打开时不处理数据，记录只在「新建」和「执行还款动作」时生成（全局约定 7），所以只能是循环处理，定时生成与一次排满全部期数都不成立。现实里分期严重逾期还可能被平台**提前终止、剩余本金一次性计入账单**，那种按全额提前结清走标注 7，金额仍由软件算。
9. **两类记录靠 `record_source` 区分**：`auto` = 软件逐期生成并算好金额的计划记录（一次一条），用户只确认「已还」；`user` = 用户主动发起的提前还款记录，用户只填动作输入，金额拆分、下一条计划重算、状态与次表进度全部由软件完成。**常规按期还款不再由用户新建或填写记录**，这是与前面最根本的差别。**同一期只留一条 `paid`**：提前还款时原 `auto` 计划记录改「已取消」、由 `user` 记录承载该期本息，避免 `total_loss` 双计。取值不写 CHECK，由业务层管。`manual_adjusted = 1` 表示该条金额被人工覆盖过，软件从该条起重算下一条 `pending`（I7）。

**分期口径提醒**

1. **I1**：不挂卡的商品 / 租金分期**进总负债合计**（实际支出只是滞后），挂卡分期仍不进；**花呗 / 白条已归信用卡账户、按挂卡分期处理，不进合计**；见主表标注 2 / 7、次表标注 7。
2. **I2**：还款计划**统一成逐期生成**，与贷款同款；见次表标注 5、附表标注 1。
3. **I3**：`start_date` / `end_date` **保持录入层校验**，DDL 仍可空，没动。
4. **I4**：计费方式**按期收**定死；取整与尾差沿用 L2（向下取整、尾差末期、末期强制归零）。
5. **I5**：提前结清规则**每笔结清时由用户选**，存该笔 `settle_rule`，不做次表字段；见次表标注 9、附表标注 7。
6. **I6**：部分提前还的重算模式**由用户选两种**，选「缩短期数、每期金额不变」时实还金额必须是每期应还额的整数倍；见附表标注 7。
7. **I7**：逾期罚息由软件按次表 `overdue_penalty_rate` 算（罚息 + 复利、不另计正常期利息、基数逾期本金，完整口径见贷款附表标注 3）、允许人工覆盖并置 `manual_adjusted = 1`；见附表标注 8 / 9。
