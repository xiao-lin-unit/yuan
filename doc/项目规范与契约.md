### 2.3 业务与统计要求

| 编号 | 要求 | 出处 |
|---|---|---|
| 要-10 | **还款计划由软件计算并写回**，用户只填动作输入；贷款侧 `fee`（本期费用）是唯一由用户还款时填的金额，分期侧全部由软件算 | 第五节标注 3/10、第六节标注 5、贷款附表标注 2 |
| 要-11 | **总负债** = `Σ 贷款剩余本金 + Σ 信用卡账户当前未还 + Σ 不挂卡分期剩余本金`；挂卡分期只作明细、不进合计。**「当前未还」就是那张卡的已用额度（`accounts.balance`）本身**，办分期时卡上欠款不动、每还一期两边各减一次，分期剩余本金**不与它相加**（同一笔钱，加了翻倍）；它不建列、打开时现算（账户草案已删 `current_unpaid` 列）。**可用额度是授信剩余，不等于当前未还**，两者相加才等于总额度 | 主表标注 2、第六节标注 7、账户草案主表「累计值口径」 |
| 要-12 | **`total_loss`（总亏损）**：贷款 = 已还各期 `interest_part + fee + penalty_amount` + 次表 `service_fee`（放款先扣服务费）；分期同式但**无 `service_fee` 项**。主表只存结果，由软件累加、用户不手填 | 主表标注 3、贷款附表标注 5、分期附表标注 5 |
| 要-13 | **「当期应还额」从负债侧查**：Σ 当期 `pending` 记录的 `principal_part + interest_part + fee`（本期该还多少）；账户侧只有累计量、查不出本期增量。**显式区分**：它 ≠ `period_installed_amount`（**本周期已办分期本金累计**，方案 A 校验用，契-9），两个量命名相近、不得互相代用 | 主表标注 8、契-9 |
| 要-14 | **同码查重**：`code` 在 A4（股票）/ A5（基金）/ A6（别的投资）三张次表各一列，「代码相同禁止二次新增」由应用层跨三张表查一遍；不收回主表、不建代码表 | 第三节第 1 条 |
| 要-15 | **批次即记录**：A4 / A5 / A6 每条买入、卖出记录本身就是一个批次，持仓数量、成本价、总成本由逐笔汇总，不另建「批次表」 | 第三节第 2 条 |
| 要-16 | **混合贷拆两笔**（公积金 / 商贷，各有自己的年利率与还款方式）；**亲友借入**归贷款 + `revolving` + 零利率无费用；**花呗 / 白条**归信用卡账户 | 第五节标注 12/13、主表标注 7 |

### 2.4 架构要求（全项目级 · 2026-11-26 用户直接下达）

> **三条需求原文**（用户口径，标点统一；第 1 条原文「更能接口」按语义作「功能接口」）：
>
> 1. **项目中的功能与页面拆分，即使要全局更换页面，也不用重写功能，而是可以直接在新页面中调用功能接口。**
> 2. **做好接口拆分，出账只是举个例子：要分析项目中的所有相关内容，将功能接口都符合该要求，不仅仅是出账接口。**（原口径：出账需要一个接口，所有账户的支出操作都调出账接口，不能在还款时写一套、消费时再写一套）
> 3. **在做好接口拆分后，注意数据库的事务问题：比如还款时调用了贷款的债务处理接口和账户的出账接口，这两个接口中的数据库操作应该保持事务一致性，不能债务处理接口的 SQL 执行成功了、出账接口的 SQL 执行失败了的情况，后者失败应当回滚前者的 SQL 执行。**
>
> **三条的关系**：一决定功能放在哪里，二决定同一功能只准有一个入口，三决定多个入口组合时 SQL 如何共进退。顺序不能倒：没有一，换页面就要重写功能；没有二，三无从谈起；没有三，拆得再干净也会写出「债务已记已还、卡里的钱没扣」的脏数据。

## 三、项目硬性规定

> 以下为不可违反项。**A 组（运行模型）优先级最高**，凡与它冲突的实现一律不成立。

### A. 运行模型 —— 最高优先级约束（全局约定 7）

| 编号 | 规定 |
|---|---|
| **硬-1** | **软件在用户不打开应用时不处理任何数据**。记录只在两个时机产生：①新建一笔资产 / 债务时，软件生成第一条待办记录；②执行还款动作时，软件算完写回当前记录、再生成下一条。除此之外不生成任何记录 |
| **硬-2** | **禁止定时生成、禁止一次生成全部计划**（「签约一次排 N 条」不成立），贷款与分期**统一成逐期生成**：还完当期才生成下一条。未来永远只有**一条** `pending` 记录。逾期状态、罚息天数、应还日判断都在用户打开 / 操作时现算现标 |
| **硬-3** | **一次补足多期只能递归**：`余额 = 本次还款额 − 本次还款记录额 − 逾期费用`，余额 > 0 则生成下一条并用余额继续还，依次类推直到归零。这就是清偿顺序，不另定「费用→利息→本金→违约金」的扣划顺序 |

### B. 范围、结构与迁移

| **契-11** | **三类还款通用**：信用卡还款、分期还款、贷款还款执行还款动作时，**付款那张卡都留一条出账记录**，记清金额、时间、还的是哪笔债（`ref_type` + `ref_id` 指过去）；不加表、不加流水类型。**「一视同仁」只指都要留付款卡出账记录，不指流水条数、不指实现复用**（契-10② C9-b 仍生效）。**信用卡还款恒定 2 条等值流水**：储蓄卡出 + 信用卡入，金额相等，`entry_type='credit_repay'`、用 `transfer_group_id` 配对，绝不调用 `transfer`；挂卡分期每还一期由负债页还款动作同事务触发（详见契-1）。**借呗放款**：账户侧一条入账 + 负债侧**同事务建一行 `az_liabilities`**，失败同滚，与 C9-a「建信用卡不建负债」并列登记。同理可推：放款 / 借钱到账写入账、基金买入选「扣款」才写出账、卖出 / 分红到账写入账；选「不扣」/「不到账」按**历史持仓补录**处理（契-14） | 账户草案流水标注 6、资产草案贷款次表标注（绑定账户 / 放款到账） |
| **契-12** | **借钱的成本 / 总亏损不双计**：**账户流水是三个统计视图的唯一真源**（取数见硬-16 / 账户草案全局约定 10）。账单出账那条 `interest` + `ref_type='debt_cost'` **只增 K2 欠款、只作界面标签「借钱的成本」，不单独计一次支出**；息费随还款 `credit_repay`（还款类出账）全额计一次，不另计、不双计。贷款 / 分期靠 `ref_id` 指向 `az_liability_loan_repay.id` / 分期还款附表对应行，**债务侧 `total_loss` 只做这一笔债维度的展示**，两处靠 `ref_id` 对齐、**不互相加**。**`ref_id` 对齐仅适用于贷款 / 分期**：信用卡不进负债表（契-10①），账单出账息费无负债侧行，`ref_id` 可空或指账单周期标识，不走对齐。**三个视图不依赖记支出模块开工**，但按品类 / 单据拆解仍待该模块 | 账户草案全局约定 10 / 11、第五节「借钱的成本」、资产草案主表标注 3 / 8 |
| **契-13** | **账单出账息费动作 / 7.7 入口**：用户打开 / 操作时按 `last_period_key` 判跨账单日 → 先归零方案 A 两列、再进新周期（不做定时归零）；同一时刻按 `credit_card_rules`（`daily_rate` / `interest_method` / 7.7 算法）**在账户侧现算**本期利息 I + 费用 F，若 `I+F > 0` 写**一条** K2 出账流水 `entry_type='interest'` + `ref_type='debt_cost'` + `record_source='auto'` → `balance += I+F`；`I+F = 0` 不写。**打开时只算展示值**（本期应还、最低还多少、按日滚利息一次性补算），**不逐日生成流水、不落表；账单出账才写一次**。最低还款只是展示值、不是分期行。该 `interest` 流水只增 K2 欠款、**不进三个统计视图**，「借钱的成本」界面标签由它承担，支出按还款类 `credit_repay` 计一次（契-12 / 硬-16）。**适用边界**：这是账户侧动作，归《账户表结构草案.md》全局约定 7；本规约硬-1 ~ 硬-3 的运行模型**只约束资产与债务模块**，不得据硬-1 判本条「多生成了记录」 | 账户草案全局约定 7 / 9、K2 标注 2、契-12 |
| **契-14** | **历史持仓补录**：开发 / 上线时用户可能**已经买入**，为方便直接创建基金或资产 → **不走账户扣款、不写账户流水**，只在资产侧生成记录。属「新建」时机，但明确**不产生账户流水、不产生债务待办记录**；补录持仓**不参与资金变动校验**，软件不倒推扣款、不报错。因此补录那一刻总资产增加、账户余额不变，是**有意的期初事实录入**，账本从这一刻起以此为起点。之后正常买入选「扣款」才写账户出账，卖出 / 分红选「到账」才写入账；未选到账的历史收益同样按补录处理。**不适用投资账户期初**：新建 K4 投资账户录的「可用金额」是账户里本来就有的真钱，按账户草案全局约定 7 写 `opening` 流水并落 `net_transfer_in` 初值，不属「不写账户流水」的补录（见契-15） | 账户草案全局约定 7、资产草案全局约定 8 |
| **契-15** | **K4 双值不相加**：剩余可用额＝主表 `accounts.balance`（复用，不物化第二份余额）；K4 次表只另存 `net_transfer_in`（净转入额，可为负、无 `>=0`）。**两者各记各的、不相加**；卖出到账 / 买入扣款**不改净转入额**，储蓄↔K4 转入 / 转出同增减两项。**本轮补充**：①**新建投资账户要录「可用金额」**（用户此前已在使用该账户、里面已有钱），作期初余额并写 `opening` 流水；②另有选填「转入金额」，**未填则该可用金额同时作为 `net_transfer_in` 初值**，填了就各记各的、不推导差额、不报错；③**K4 余额调整是可用金额调整**，`net_transfer_in` 按同一差值同增减（`append` 同事务，`in` 加 / `out` 减）。「总额 = 股票市值 + 剩余可用额」详情页现算，市值由资产侧 A4 决定、不进账户表 | 账户草案 0.3 / 全局约定 7 / K4 标注 / 第五节边界表 |
